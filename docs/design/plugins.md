# Plugins

OxiGuitar is a small core and a set of plugins. The core opens nothing and plays nothing by itself: it holds the score, shows it (and exports what it shows as a PDF), edits it (Infer Key Signatures included), and drives the player's transport. Every file format, every sound, every other export and tool, and every feature that depends on a platform or environment is a plugin (Mateus, 18 Oct 2026).

This document is the design, accepted by Mateus on 18 Oct 2026 with his answers to the questions in ADR 0008 ([docs/adr/0008-plugin-architecture.md](../adr/0008-plugin-architecture.md)), and amended the same day: PDF export and Infer Key Signatures stay in the core, and the core has no catalogue of formats (ADR 0008, "Amendments"). The plugin developer guide (how to write one, step by step) lives in the user manual's sister book, `docs/plugins/` ("Writing a plugin", below).

## Why

- **Small, simple core.** Read, edit, write, show (with PDF export) and the player's controls. Everything else can be added, replaced or dropped without touching the core, and the mobile apps (M10) start from the same small base.
- **No dead code.** The app never carries or loads code it cannot use on the machine it runs on: no Wayland code under X11, no CoreAudio code on Linux, no reader for a format nobody opens. Less code loaded means a smaller attack surface and a faster start.
- **One format per plugin.** Each file format is its own plugin (one for .gp3, one for .gp4, one for .gp5, one for .gpx, one for .gp, and so on), so a format can be added, improved or retired on its own.
- **Partitioned testing and work.** Each plugin is its own crate with its own tests, fuzz targets and CI path filter. Contributors can own one plugin without learning the whole codebase, and several plugins can be built in parallel.

The core compiles per target, so a Windows build holds no Linux code. On Linux the windowing toolkit would carry both X11 and Wayland in one binary, so **there are two Linux builds of the core** (Mateus, 18 Oct 2026): a Wayland build, the main one, and an X11 build for desktops that still need it. X11 is deprecated from the start, as the desktops are leaving it, and the X11 build will be dropped. Each build enables only its own Slint and winit backend (`backend-winit-wayland` or `backend-winit-x11`), through a Cargo feature of `oxiguitar-app` (`wayland`, the default, or `x11`).

| Build | Linux packages | Notes |
| --- | --- | --- |
| Wayland | `oxiguitar` (.deb, .rpm), `OxiGuitar-VERSION-x86_64.AppImage` | The default. Headless tests run it in a private headless Weston (`scripts/package/in-wayland.sh`; NET-5 and the package tests). |
| X11 (deprecated) | `oxiguitar-x11`, which Provides, Conflicts with and Replaces `oxiguitar`; `OxiGuitar-x11-VERSION-x86_64.AppImage` | Same program, X11 backend only. Its window says nothing different; the manual says it will be dropped. |

As built (slice 4):

- `oxiguitar-app` has the features `wayland` (default: `slint/backend-winit-wayland`, `rfd/wayland`) and `x11` (`slint/backend-winit-x11`); a build with neither doesn't compile. Slint's own `unstable-winit-030` feature would turn on both display systems, so the app takes the raw window events (the wheel, Ctrl + wheel, file drops) from `i-slint-backend-winit` directly: the crate `slint::winit_030` re-exports, with no features of its own, at the exact version Slint pins.
- The app tells the host its build's display system for plugins' conditions (`wayland` or `x11`), instead of guessing from the environment. A build started in a session it can't use (the Wayland build without a Wayland compositor, the X11 build without an X server) says which build to install instead, and exits.
- **Wayland first** (Mateus, 19 Oct 2026; [ADR 0009](../adr/0009-wayland-first.md)): the Wayland build takes the Wayland path, and workarounds belong to the X11 build until it is dropped. **Our code never looks at the environment to choose what to do** (Mateus, 17 Nov 2026; [ADR 0011](../adr/0011-no-environment-checks.md)): each build knows its display system when it is built (`DISPLAY_SYSTEM`; a build with both features doesn't compile), and programs that draw nothing say `oxiguitar_host::NO_DISPLAY`. Libraries are theirs; other people's plugins may, but shouldn't (nothing checks them). So Slint follows its latest release (1.19.0, whose Wayland clipboard uses the window's own connection, as 1.17.1's did; its winit backend also compiles arboard, which the Wayland build never reaches).
- `scripts/check-display-crates.sh` (CI's "Lint and docs") fails unless each build turns on its own windowing backend in Slint's winit backend and in winit, and not the other one, on x86_64 and ARM64 (ADR 0011: our choice, not the libraries' crates), and that no tracked Rust file of ours names a session variable (`WAYLAND_DISPLAY`, `DISPLAY`, `XDG_SESSION_TYPE`…). CI also lints the X11 build, runs NET-5 on both builds (the Wayland one in a headless Weston, the X11 one under Xvfb), and the release workflow packages, installs and starts both (in Debian sid, Fedora and as AppImages; installing `oxiguitar-x11` replaces `oxiguitar`).

- **Toolbar**: sections of icon buttons, side by side. The core has File, Edit and View sections; a plugin can add sections with its own icons. It can be hidden (View → Toolbar).
- **Four areas**: top and bottom span the window's width; left and right sit beside the page. Each holds tabs. Clicking the active tab's name, or the chevron, collapses the area to its tab strip; View → Panels hides it completely. Plugins add tabs to any area.
- **The page** sits in the middle on a dark canvas (the same colour as Dark Page's surround, whichever page colour is shown). It has no tabs and cannot be hidden.
- **Footer**: one line at the bottom with the latest message. Clicking it expands a scrollable list of this session's errors and warnings (it isn't a log: Mateus, 19 Oct 2026); clicking again shrinks it.
- **Player controls** live in the top area's Player tab, with the choice of output plugin. With no output plugin installed the controls are greyed out and the footer says where to get one.

Before M2 the containers exist with placeholders (Palette and Inspector say what will go there; the toolbar's Edit section is greyed). `docs/design/ui.md` describes the window as built.

## Plugin files

A plugin is **one native library file** (accepted, 18 Oct 2026) with a small, versioned C interface, built per target, with its manifest in a named data section.

- **One file**, named `NAME.oxp` ("OxiGuitar plugin"), for example `gp5.oxp`. Inside it is an ordinary shared library for one target: ELF on Linux, PE on Windows, Mach-O on macOS (one universal file for Intel and Apple Silicon). A plugin published on its own carries the target in its download's name (`example-0.1.0-linux-x86_64.oxp`); the user can drop it in a plugin folder as it is. Ours come together, in one zip per system (below). Icons, strings and small data are compiled into the file. Large data (sound sets, NAM models, impulse responses) is never in the plugin file and never downloaded: the user puts it in a folder (sound sets in `soundfonts`, beside `plugins`; Mateus, 21 Oct 2026), and a plugin keeps what it makes in its data folder (docs/design/player.md).
- **No unpacking.** The operating system maps the file into memory when it is loaded; nothing is copied, unzipped or compiled at start.
- **Manifest without loading.** Each plugin carries a manifest, JSON text, in a section named `oxg_manifest` (in the `__DATA` segment on macOS; on Windows `oxgmanif`, because section names in PE executables and libraries hold at most eight characters). The author writes it as `manifest.json` beside the plugin's `Cargo.toml`, and the SDK's `export_plugin!` puts the file's bytes in the section. The host reads it with the `object` crate, which parses the file's headers and reads only that section, without running any of the plugin's code. Reading a manifest takes well under a millisecond. Keys a host doesn't know are ignored, so a newer plugin's manifest still reads in an older host; the SDK's checks reject unknown keys when the plugin is built, so typing mistakes are caught there.
- **Loaded only when needed.** At start the host reads manifests only. A plugin's code is loaded the first time one of its contributions is used: opening a .gp5 file loads the GP5 plugin; pressing Play loads the chosen output; showing a tab loads the plugin that owns it. A plugin whose conditions don't hold (a Wayland-only plugin under X11, say) is never loaded at all.
- **Never unloaded in a session.** Unloading native code safely is unreliable (thread-local destructors, threads a plugin started). Disabling a plugin takes effect at the next start; the plugin manager says so.

### The interface

- One exported symbol, `oxiguitar_plugin_v1`, returns a table of `extern "C"` functions. The `v1` is the interface's major version: a host refuses a plugin built for another major version, with a footer message naming the plugin and the version it needs.
- Calls pass **messages as bytes**, encoded with a stable, versioned schema (`oxiguitar-plugin-api`, serde + postcard). Answers come back through a "sink" the caller provides: the callee hands it bytes and the caller copies them, so memory is never freed on the other side of the interface and the two sides may use different allocators.
- **The score crosses as its own types**, `oxiguitar_plugin_api::score`, which mirror the model field for field but belong to the interface (version 1, its encoding pinned by a test). The core converts between the two (`oxiguitar-model`'s `wire` feature; every fixture, reference and corpus file crosses without loss). So the model can keep changing as the editor grows; a change that plugins must see goes into a new version of the wire score, beside version 1.
- **Versions**: the interface's major version is in the entry symbol's name and the manifest; a minor version only adds (new messages, new variants at the end of an enum, new fields at the end of a C table, new manifest keys), and the host sends a plugin only what its minor version knows. Version 1.0 has formats, instruments (declared), services, footer messages and settings; **1.1** adds tabs, the canvas's display list, pushed events and the open score (slice 3), each at the end of its enum; **1.2** (M3 slice 2, frozen with v0.5) adds the score version 2 (version 1's tree with a list of extensions on each part, which later minor versions extend at its end, so no version 3; free time first), the editor's selection (`Selection2`: caret with voice and string, beats of a voice, bars across tracks), tools in the Tools menu (manifest `tools`, `Request::Tool`) and changes to the score (`HostRequest::Score2` gives it with its revision, `HostRequest::Apply { revision, name, score }` hands it back, recorded as one undoable command unless the score changed since). The host sends a 1.2 plugin `Write2`, `Selection2` and the score without extensions newer than its version; older plugins get version 1, and what version 1 can't hold is named in a write's losses. **1.3** (M4, frozen with v0.9) adds settings windows, track-dialog sections, footer links, the plugins' folders, instruments and effects on the audio thread, audio devices and the `cpu` condition (docs/design/player.md, "The plugin interface (1.3)"); **1.4** (frozen with v0.11, #165; the SDK crates are at 1.4.0) adds a link among a tab's widgets (`Widget::Link`), which the core opens in the browser, `https://` only, as it does the footer's links (Mateus, 27 Oct 2026: the sound plugin's settings window links to the manual's Better sounds page), and **exporters** (M4 slice 7; Mateus, 1 Nov 2026): manifest `exporters` (id, name, extension, kind), entries of File → Export; kind `audio`, the only one so far, gets the score's sound: `Request::ExportStart` (answered with the rate wanted and the file's first bytes), `ExportSamples` (interleaved stereo f32, answered with the bytes that follow), `ExportFinish { cancelled }` (the last bytes, and bytes to write over the start: a header naming the length). The core renders through the player (`oxiguitar_play::export`), writes the file under a temporary name and renames it; the plugin never touches files. **1.5** (frozen with v0.14, #232; the SDK crates are at 1.5.0) adds effects that follow their track's settings while the song plays: `Request::UpdateEffect { instance, prepare, previous }`, answered with `Answer::Updated(bool)`, the one request that may name an instance the audio thread is running; the SDK's `Effect::update` makes an `Update` off the audio thread and its glue leaves it in the instance's lock-free mailbox for `Processor::apply` before the next `process` (docs/design/player.md, "Track sections while playing"). A plugin file carries its SDK's minor version, which the loader refuses when newer than its own, so a plugin built with the 1.5 SDK needs v0.14 whatever its manifest says. **1.6** (v0.17, the rest of the palette; the SDK crates are at 1.6.0) adds only extensions of the score version 2 (`since` 6): fermatas on master bars, simile signs on bars, slurs, hairpins, ottavas, slash notation, beaming, forced tuplet groups, barres, fade-outs and volume swells, slight bridge vibrato, pedal, wah, arpeggios, rasgueado, golpe, pick scrapes and dead slaps on beats, wide vibrato, ornaments, string numbers and spellings on notes, and bars per system on the score and on tracks (docs/design/palette.md); version 1's own fields keep what they held, so an older plugin still sees a fade-in and a vibrato. A write by any plugin older than the score's extensions now names, among its losses, each kind of mark it couldn't receive. **1.7** (v0.18, #223; the SDK crates are at 1.7.0) adds two signature tests for XML formats, which no fixed offset can recognise: `xml_root`, the file's first element past a byte order mark (UTF-16 decoded), the declaration, comments, processing instructions and the document type, within its first 64 KiB; and `container_root`, the same for the first root file that a ZIP container's `META-INF/container.xml` names, inflating at most 64 KiB of each member (compressed MusicXML, `.mxl`, holds its root file's name in that list, so a member's name can't recognise it). An older host files them under tests it doesn't know, so such a signature never matches there. `Signature::smallest_file` gives the least file a signature recognises, which the contract suite reads as "its signature alone". Interface 1 is frozen from the OxiGuitar 0.2 release: later versions only add.
- **Audio crosses as raw sample buffers**, with no encoding and no allocation, so instruments run at full native speed on the audio thread.
- The host hands each plugin a table of **host services** at start. Built: send a footer message, read and write its own settings, call a service it `requires`, and (1.1) ask for the open score and redraw its tab. Built for the editor (1.2): the score version 2 and submitting a change, always as one change the user can undo, never by changing the score directly. Built for the player (1.3, below): the plugin's folders, footer messages with a link, a settings window and sections of the track dialog. To come, each when a real plugin needs it: parts of the score (a track, the selection, a range of bars). No host service downloads anything (Mateus, 21 Oct 2026).
- The **SDK** (`oxiguitar-plugin`) wraps all of this in safe Rust: a plugin implements traits (`FormatReader`, `FormatWriter`, `Service`, `Tab`; since 1.2 `FormatReader2`, `FormatWriter2` and `Tool`; since 1.3 `TrackSection`, `Instrument` and `Effect`; `Exporter` when it joins the interface) and calls one `export_plugin!` macro. Plugin authors write no `unsafe`.
- **Licences**: the interface (`oxiguitar-plugin-api`) and the SDK (`oxiguitar-plugin`) are **MIT OR Apache-2.0** (Mateus, 18 Oct 2026), so a plugin, which compiles the SDK into itself, may use any GPL-compatible licence. The core stays GPL-3.0-or-later, and our own plugins are GPL-3.0-or-later like it. A plugin that is not GPL-compatible isn't possible in practice: it runs inside the app, which includes Slint under its GPL-3.0-only option.
- **Where the `unsafe` is.** Loading a native library and calling through function pointers is `unsafe` in Rust by nature; no plugin system with native code can avoid it. It lives in exactly two small modules, the host's loader (`crates/oxiguitar-host/src/loader.rs`) and the SDK's export glue (`crates/oxiguitar-plugin/src/glue.rs`, plus the two attributes `export_plugin!` generates: the manifest's section and the entry symbol), reviewed line by line, every block with a `// SAFETY:` comment, and covered by the contract suite on every system CI tests. Their crates, and plugin crates, deny `unsafe_code` and allow it only there (a crate that forbids it can't allow it in one module); the rest of the workspace keeps `unsafe_code = "forbid"`, and a test fails if `unsafe` is allowed anywhere else. Mateus accepted this (18 Oct 2026): it is the price of native plugins, not a workaround around another library. Interface 1.3 adds to the same two modules the audio thread's calls (instances as boxes whose addresses the host names, the render and process calls, and the counting allocator `export_plugin!` installs); and the contract suite has a third, test-only module (`crates/oxiguitar-plugin-test/src/syscalls.rs`, Linux: fork, seccomp, a signal handler) that catches system calls while a plugin renders. It is never shipped.
- **The same plugin can be built in.** A plugin crate builds both as a `.oxp` and as an ordinary Rust library. The mobile apps link their plugins in (iOS forbids loading downloaded code), and our own tests use plugins as libraries without going through the interface.

### How the host loads and chooses

As built in `oxiguitar-host` (`Plugins`):

- **At start**, every `.oxp` file directly in the plugin folders is examined, in folder order and then by name, and nothing is loaded. A file is usable when its manifest reads and is valid, it is whole (every segment its headers describe lies inside the file, so a truncated download is refused before it is loaded), it is a library for this system and processor (one universal Mach-O file holds both of the Mac's), its interface is 1.x with a minor version this host has, its conditions (system, processor, display system, and since 1.3 the processor's features, `cpu`) hold, and settings.json doesn't list its id under `disabled`. Of several usable files holding one plugin id, the highest version is used, then the one needing more processor features (a faster build this processor can run), then the one in the later folder (the user's over the system's), then the earlier file name in one folder. The `cpu` key is valid only in a manifest that asks for interface 1.3 or later: an older host, which would ignore it, refuses such a manifest, so no host ever loads code on a processor the manifest says can't run it; a feature name the host doesn't know counts as missing. The footer names the plugins found, and every file that can't be used and why.
- **One file per plugin id**: the highest version is used; on a tie, the build needing more processor features, then the file in the later folder, so a copy in the user's folder wins over the installed one (Mateus, 1 Nov 2026: what #166 meant; the earlier folder used to win), then the earlier name in one folder. The others are reported as replaced (and left out of the plugin manager's list). The processor-features step is for one plugin shipped in two builds at one version, as the NAM plugin is on Linux x86_64 (`nam.oxp` and `nam-x86-64-v3.oxp`): both are usable on a processor with AVX2 and FMA, and the build made for it is several times faster, so it is used whatever the files' names and folders; a processor without those features can't use that build, so it gets the other. It was taken out in #166 and brought back (Mateus, 1 Nov 2026); what #166 fixed stays: the system folders are always searched, before the user's, and replaced files are not listed twice.
- **Loaded on first use, never unloaded.** The host loads a plugin when a contribution of it is first used, checks that its table carries the same manifest as its file's section and was built for an interface the host has, and starts it once. A plugin that fails to start is withdrawn (below). A plugin asking for its own contributions while it starts gets an error instead of waiting forever.
- **Formats**: a file's format is found from the signatures in the manifests, without loading anything; the first usable plugin (in folder order) with a matching signature reads it. The formats of the usable plugins are all the core can open: it detects nothing itself and names no plugin it doesn't have (Mateus, 18 Oct 2026). With no plugin installed it opens nothing.
- **A file no plugin recognises** is refused, and the footer says so. When a usable plugin declares the file's extension among its formats' extensions (a `.gp5` file the Guitar Pro 5 plugin doesn't recognise), the message asks for a bug report at the issue tracker; otherwise it says no installed plugin opens this kind of file and asks for a feature request there.
- **Instruments**: the player offers a track the instruments whose classes include the track's (`InstrumentClass::of(program, percussion)`).
- **Services**: for an interface, the candidates are the services of usable plugins whose own conditions hold. settings.json may pin one, as `"services": {"INTERFACE": "PLUGIN-ID/SERVICE-ID"}`; otherwise the highest `priority` comes first, then plugin order. Each candidate's probe is asked in turn whether it works here (loading its plugin), and the first that says yes is used for the rest of the session. A pin that can't run here is skipped, and said so if nothing else works.
- **Host services**: a plugin's footer messages carry its name; its settings are the object under its id in settings.json, saved at once through the one copy of settings.json the app also uses; it may call only the service interfaces its manifest lists under `requires`.
- **Errors and panics**: a plugin's error crosses with its kind, offset and context. **A plugin that fails is withdrawn, as if it weren't installed** (Mateus, 19 Oct 2026): one that can't be loaded or started, crashes (a panic, caught in the plugin), or breaks the interface's contract (an answer that can't be read or wasn't asked for, tab contents the core can't show) is not used again this session, and everything else goes on as if it had never been installed: its formats, tabs, services, instruments and events are gone, a file it would have read goes to the next plugin that recognises it, and a service is chosen again among the others. The footer says so once, as an error, and the plugin manager shows why. An error a plugin answers with (a damaged file, a widget it refuses) is an answer, not a failure. (A plugin built with `panic = "abort"` takes the program down instead.) As built: `Found::failure`, `Plugins::open` (recognise and read, falling back to the next plugin), `call_service` choosing again, `Core::withdrawn` (the window takes the plugin's tabs away), and the contract tests with `plugins/test-second`, a second test plugin reading the test plugin's format.
- **Threads**: any call may come from any thread. A program has one `Plugins`: the system loads a library file once per process, so a second host over the same file would find the plugin already started.

### Tabs and events (interface 1.1)

As built in slice 3 (`oxiguitar_plugin_api::tab`, `display` and `event`; the host's `Plugins::tabs`, `tab_content`, `tab_event`, `push`):

- **A tab** is declared in the manifest (`"tabs": [{"id": "tuner", "title": "Tuner", "area": "bottom"}]`; areas `top`, `bottom`, `left`, `right`), so the window shows its name without loading the plugin. When the tab is first shown, the host asks the plugin for its contents (`Request::Tab`), which loads it.
- **Contents** are rows from top to bottom, each holding widgets from left to right: a label (plain or muted), a button, a toggle, a slider, a one-line field, a choice (drop-down), a list with one selected line, and a canvas. The core draws them in the window's own style, so every plugin looks like the rest of OxiGuitar and follows Dark Interface by itself. A shape this simple shows the same way in every area and, later, on mobile.
- **The user using a widget** is sent to the plugin (`Request::TabEvent`: a click, a tick, a slider let go, Enter in a field, an option or line chosen, the pointer on a canvas), and the plugin answers with the tab's new contents. A plugin whose tab changes on its own (after an event, say) asks the host to redraw it (`HostRequest::Redraw`); the window asks for the contents again when the tab is on screen.
- **The canvas** is drawn with the display list's wire form, version 1 (`oxiguitar_plugin_api::display`): lines, rectangles, paths (filled and stroked) and text, in the canvas's own units with y pointing down, coloured by role (ink, page, accent, muted) so the window's theme resolves them. Text crosses as text and the core places it with its own fonts (the text font, or the music font with SMuFL code points), so a plugin needs no fonts. The core scales the canvas to the room it has, keeping its proportions, and reports pointer positions (down, drag, up; which button) in the canvas's units; drags the plugin hasn't answered yet are merged. A canvas is at most 100,000 units a side and 100,000 items, and everything on it stays within its reach: every point within the canvas extended by its own size on every side, no size or line width over three times its longer side (the `plugin_tab` fuzz target found that a line 10²⁰ units long made the renderer fail); text running past that reach is cut there. `oxiguitar-display`'s `wire` feature turns it into the core's own display list, drawn by the same renderer as the score.
- **Contents the core can't show** (an id missing or used twice, a slider whose range is backwards, a choice of an option it doesn't have, a canvas that is empty, too large, or holds a number that isn't finite) are refused with a sentence that names the first problem, and the tab says so; the plugin's other tabs carry on. The SDK's `check`, run by `cargo test`, catches them before a plugin ships.
- **Events**: a plugin lists what it wants under `"events"`: `score` (a score was opened, changed or closed; each carries a revision number, never the score itself), `selection` (a run of beats in a track, or nothing) and `playback` (playing or not, the beat the cursor is on, and the time in seconds). The host pushes each event to every usable plugin that subscribes, loading it the first time one fires. They are delivered in order, on one thread of the host's that sleeps until an event arrives; nothing polls. Events that say where something is now (the selection, the playback position, the score's revision) replace one of the same kind still waiting at the end of the queue, so a slow plugin gets the latest rather than a backlog. A plugin that answers an event with an error is named once in the footer; one that crashes on it is withdrawn.
- **The open score**: a plugin that needs it after a score event asks for it (`HostRequest::Score`), so the score is converted and sent only to plugins that use it, when they use it.
- Today the app sends score events. Selection events come with the editor (M3) and playback events with the player (M4). The interface already carries both, and the contract suite tests them through the host.

### Interface 1.3 (the player)

Built in M4's slice 2, first part (docs/design/player.md); instruments, effects and audio devices on the audio thread come next, in the same minor version. Additions only:

- **A settings window** (retired in interface 1.9, ADR 0012): a manifest with `"settings_window": true` got a Settings… button in the plugin manager, which opened a window the core drew around the plugin's widgets. A plugin now shows its settings in a dialog of its own, opened by a tool with `"edits": false` ("Interface 1.9" below).
- **Sections of the track dialog**: `"track_sections": [{"id", "title", "plays"?, "does_not_play"?}]` (instrument classes, as instruments name them). The dialog shows each section for the tracks of its classes, under a line and its heading. The plugin keeps nothing: each request carries the track (`TrackInfo`: index, name, class) and its settings for that plugin, a JSON object (`Request::TrackSection`, `Request::TrackSectionEvent`; answered with `Answer::TrackSection`, the contents and the settings). They change while the dialog is open; OK makes them part of the dialog's one change (undoable), Cancel drops them. The model keeps them per track (`Track::plugins`, by plugin id). No format holds them, so they are saved beside the score in **`FILE.oxg`**, the score's whole file name plus `.oxg` (`song.gp3.oxg`; Mateus, 25 Oct 2026): JSON, `{"oxiguitar": 1, "tracks": [{"name", "plugins": {ID: {...}}}]}`, written when the score is saved (beside first, then in place; not at all while no track has any and there is no .oxg yet), read when it opens (a track whose place changed finds its entry by name), copied by `oxiguitar-cli convert` (`oxiguitar_host::sidecar`). An .oxg that can't be read is said in the footer, and the score opens with the settings empty.
- **Footer messages with a link** (`HostRequest::Notify2`): the text, then the link's words in the accent colour; a click opens the address in the browser. Only `https:` addresses with a host are taken (`oxiguitar_host::is_https`; the window's opener checks again).
- **Advice** (`HostRequest::Advise(Advice)`, interface 1.4; the guide's Advice page): a dialog a plugin asks the window for, with an id, a title, a text and up to three `https:` links (`Advice::problem` checks the limits: id 1 to 64 of `a-z0-9-`, title 80, text 1200, link words 60). The host (`Plugins::advise`) refuses a plugin built for less than 1.4 and bad advice with an error, leaves out what the user silenced (`oxiguitar_host::advice::is_hidden`) and passes each (plugin, advice) on to `Core::advise` once a session (`Inner::advised`); never in safe mode. The window (`crates/oxiguitar-app/src/advice.rs`, `AdviceDialog` in app.slint) keeps a queue behind a lock, since plugins ask from any thread before the window exists, and shows one dialog at a time once it is up. Ticking "Don't show this again" calls `advice::hide`, which saves `"advice": {"<plugin id>": {"<advice id>": "hidden"}}` in settings.json through `SharedSettings::update` (one atomic change; every other key and entry stays). The core's own advice (PR 5) uses the plugin id `oxiguitar` through the same dialog. Links open only when clicked, through the window's one opener.
- **The core's startup check** (PR 5): `Inventory::advice` turns what the manifests say into advice under the plugin id `oxiguitar` (`advice::CORE`), most important first: `no-format-plugin` (no reader), `no-player-plugin` (no instrument) and, only when an instrument exists, `no-output-plugin` (no `audio-device` service declared by a usable plugin whose conditions hold, `Plugins::declared_services`; nothing is loaded or probed, and exporting audio works without one). Each links to the manual's page of official plugins and its install page for this system (`install_page`; `install-linux.html#appimage` when `APPIMAGE` is set, since the AppImage holds the core only from 1.0). `Startup::advice` carries them, left out when the user silenced them (`advice.oxiguitar.<id>`), empty in safe mode and for `find` (programs without a window); the app queues them with the plugins' advice. The footer's notices about the same gaps stay. The text names the user's plugin folder.
- **The plugin's folders** (`HostRequest::Folders`): its own data folder (`data/<plugin id>/`, below) and cache folder (the system's place for caches), made on first ask, and the shared folders its manifest lists under `"folders"` (`soundfonts`, `nam`, beside `plugins`), which the app creates at start when any usable plugin lists them. Paths cross as UTF-8 text.
- A track section holds the widgets of a tab without a canvas; contents with a canvas are refused. It travels through the window's plugin thread, as tabs do, so a slow plugin never holds the window up.
- The SDK re-exports serde_json (`oxiguitar_plugin::serde_json`), since settings and track sections speak JSON objects.
- **Audio devices** (third pull request): the service interface `audio-device` (`open`, `close`, `devices`; `oxiguitar_plugin_api::audio_device`) and the host table's new last field, `render`, which a device plugin calls from its audio callback (the SDK's `Host::audio_out`). Our four device plugins and their shared crate are in docs/design/player.md, "The audio devices, as built". A plugin whose system library is missing (libpipewire) is withdrawn without a footer error, and the plugin manager says "Can't run here" and why.
- **Instruments and effects** (second pull request): the manifest's `instruments` come alive, and `effects` (the same shape, by class) join them. Off the audio thread the host prepares one (`Request::Prepare` with the rate, the largest piece and each track's program, tuning, capo and track-section settings; `Request::PrepareEffect` for one track) and gets an instance with its latency and its resolution (`Answer::Prepared`); `Request::Release` frees it. On the audio thread, plain C calls with no messages: the plugin table's new last field points to a `RealtimeTableV1` (`render`, `process`, `allocations`), read only from plugins built for 1.3 (an older plugin's table ends before it; the loader reads only interface 1.0's fields from those). A render call carries its events (all on its first frame), the timeline's pitch points, the score's time and seconds per frame, and two buffers per track, at most 128 (64 tracks). A panic in a render is caught; the instance is silent from then on and its plugin is told. SDK: `Instrument::prepare` → `Renderer::render(&mut Piece)`, `Effect::prepare` → `Processor::process(left, right)`; the host: `Plugins::playable`, `effects_for`, `prepare`, `prepare_effect`, and `realtime::Instance`, which owns its call's buffers so rendering allocates nothing and releases the plugin's instance when dropped (off the audio thread: the engine hands sources back first).

### Interface 1.8 (plugins own their tools, #250 and #293)

Mateus, 15 Nov 2026: a contributor's tool is on the palette without a change to the core, and the wah shows it: the core's palette loses its two wah tools and the wah plugin brings them. #293 asks for the rest: palette tools and menu items with dialogs, inspector tabs with widgets (1.1 has them), sound processing steps (1.3), following what is played and reading what is engraved, steps a user reorders in the Track tab (#152 has it), and all of the core's data. Decided with him: the cleanest and most robust way, with no regard for compatibility (the app is unreleased and every plugin is rebuilt); menus existing, new and right-click; the engraving read and drawn on.

- **Still one interface, extended at its end.** "Full access" is not the core's crates linked into plugins: that would tie every plugin to one build of the core, and a crash or a type change there would be every plugin's. The score crosses whole already (version 2, with every mark as an extension, handed back as one undoable change); 1.8 adds what was missing around it. Nothing existing changes, so released plugins keep loading.
- **Tools anywhere** (manifest): `ToolSpec::palette` (`section`, one of the core's or a new one after them; `symbol`, a SMuFL code point of the music font, or `text` of at most 5 characters) and `ToolSpec::menu` (`file`, `edit`, `view`, `tools`, `help`, `page` and `track` for the right-click menus, or a new menu's name, placed between Tools and Help). The palette holds plugin tools as buttons with the id `plugin:PLUGIN:TOOL`; a click runs the tool on the worker, as the menu does. Sections and menus the plugins name are made as needed; the palette's search and keyboard walk include them.
- **Where things go by default** (Mateus, 16 Nov 2026: most of OxiGuitar will be plugins, and the core is the framework): everywhere a plugin adds something, its author names a place of the core's, names a new one, or names none and gets Plugins (`manifest::PLUGINS_PLACE`): the Plugins menu (tools without `menu`, and every tool of a plugin built before 1.8; they were in Tools), the palette's Plugins section (`palette` without `section`), the right area for a tab without `area`. The core puts nothing of its own in either Plugins place.
- **Dialogs** are tabs whose `area` is `dialog`: the same thread, widgets and canvas as a tab, shown on a card over the window with OK and Cancel of the core's. `HostRequest::OpenDialog { tab }` opens one (one at a time), `Request::TabClosed { tab, ok }` tells the plugin how it was closed (`Tab::closed`). `HostRequest::ShowTab` brings an ordinary tab to the front.
- **The selection, asked for**: `HostRequest::Selection`, answered with the `Selection2` the window last told the worker (it tells it on opening too), so a tool needs no event subscription and works before the caret ever moved.
- **A plugin's own data anywhere** (Mateus, 16 Nov 2026: notes and bars too, structural, so now): `ScoreExt`, `MasterBarExt`, `BarExt` and `NoteExt` gained `Plugin { plugin, data }` like the beat's; the model holds `plugins` on `Score`, `MasterBar`, `Bar` and `Note`; `Track::kept`/`Track::keep` list and restore a track's places by path (`[staff, bar]`, `[staff, bar, voice, beat]`, `[staff, bar, voice, beat, note]`); the sidecar keeps `"plugins"` and `"bars"` at the top and `"kept"` per track. Edits: pasted bars and simile copies carry it, a cleared bar keeps its own, new and re-barred bars start empty, a tied continuation note starts empty.
- **A plugin's own data and marks on beats** (the first form): `BeatExt::Plugin { plugin, data }` (a JSON object as text) and `BeatExt::Mark { plugin, text }` (at most 16 characters, drawn in the technique lane after the wah's sign). The model holds them on the beat (`Beat::plugins`, `BeatEffects::marks`), so they follow every edit, copy and undo with no code of their own. No format holds them: `Plugins::write` strips them before any format plugin sees the score (`Score2::drop_plugin_data`) and names no loss, and the sidecar keeps them by track and place (`"beats": [{"at": [staff, bar, voice, beat], "plugins": {…}, "marks": {…}}]`). Chosen over settings keyed by a beat's address, which every insertion would have shifted.
- **Drawing on the page** (Mateus, 16 Nov 2026: hooks over the stable interface rather than native plugins, as long as they cost little, limit plugin authors in nothing practical, and the core holds nothing of any plugin's): a plugin whose manifest `draws` is asked, before each engraving, about the places that carry its data or marks and only those (`Request::Draw { places }`: a staff's bar with its data, or the whole beat in version 2), and answers boxes of canvas items in staff spaces (`Drawn`, at most 40 by 40 and 2000 items). The host keeps each plugin's last request and answer and doesn't ask again for the same places (`Plugins::draw`; `try_draw` for the contract suite). The app (`drawings.rs`) gathers the places (`wire::beat_to_wire2`, one beat at a time, never the whole score) and gives the engraver `Options::drawings` (`oxiguitar-layout/src/drawing.rs`: `Drawings`, `Drawing`, `Shape`), which knows nothing of plugins: a lane of its own above the staff, the outermost, as tall as a system's tallest box; boxes from the beat's column rightwards, a bar's at its first beat; the column made wide enough. So a drawing is printed, exported and hit-tested as the rest. Text marks (`BeatExt::Mark`) stay, as the way to draw a few characters with no code. **Clicks**: each `Drawing` carries an opaque `tag` (the app's index among the drawers) and the engraver records each box with its place and tag in the hit map (`SystemHits::drawn`, `Hits::drawn_at`); a click there, after the caret moves, goes through the worker to the plugin as `Request::Clicked` (the place as the score has it now, the point in staff spaces, double or not), answered like a tool's run.
- **Playing the notes its own way** (the same decision): a plugin whose manifest `performs` is asked, when the song is got ready to play or export, about each track (`Request::Perform`: the track's notes in the form instruments get them, with their staff, voice, visit and beat, the bar of each visit, and the beats with marks or data as `PlayedBeat`s), and answers the notes as they should sound (`Answer::Performed`). Performing plugins take turns in plugin order. The host keeps each plugin's last request and answer by track and doesn't ask again for the same (`Plugins::perform`; `try_perform` for the contract suite), and checks the answer against the interface's limits (`PlayedNote::problem`, `PERFORMED_MAX`); a failure leaves the track as written. `oxiguitar-play`'s `plugin_source::perform` replaces the timeline's notes before the schedule is made, in the app's sound thread, the command line's player and audio export, so the cursor and practice follow what is played. Chord voices aren't given.
- **Reading the engraving**: `HostRequest::Engraving`, answered with the pages' drawing as the canvas's display items and each beat's box and page (`Engraving`, `EngravedPage`, `EngravedBeat`). The worker publishes what it engraved for the window to the shared open score (the pages behind an `Arc`, converted when asked), so the answer needs no trip through the worker, which is the thread a tool runs on. A warning's red and a track's own colour are ink there; the interface has four colour roles.
- **Following what is played**: effects with `follows_score` (docs/design/player.md, "Effects"). Playback events (1.1) already tell tabs where the cursor is.
- **Order of processing steps**: the user's, per track, since #152; the default was a list of plugin ids in the core and is now each effect's `order` in its manifest, so a new pedal needs no change here.
- **No format is "the fullest"** (Mateus, 16 Nov 2026): the core named Guitar Pro 7's format as the one that holds most and saved into it when a file's own format lost something; for a while a manifest key, `fullest`, said so instead. Both are gone: the core can't know what formats plugins bring. Save writes the file's own format; when the writer names losses, the question offers **Keep Them in the .oxg File** (the whole score, version 2 as JSON, goes into the sidecar under `"score"` with the length and a check sum of the score file written; `sidecar::KeptScore`, `Kept`), **Save Without Them**, or Cancel. Opening uses the sidecar's score while the file is still those bytes, says so when another program changed the file, and the choice holds for later saves of that file. A file whose format no plugin writes asks for Save As.
- **The test plugin** uses each: a palette tool with text and a menu of its own (`stamp`: data and a mark on the first beat, the engraving and the selection read), a palette tool with a symbol in a new section and the page's menu (`ask`: a dialog, and a tab brought forward), and a gain that follows the score (silent under the stamped beat). The contract suite checks every tool, dialog and following effect of any plugin.
- **Keys** (hooks, 16 Nov 2026): `ToolSpec::shortcut` (`manifest::Shortcut`: Ctrl or Alt required, one character key). The window tries them last, after the player's, the caret's and the editor's keys (`on_edit_key`), so a plugin can't take a key of the core's; between plugins the first in plugin order keeps them (`Plugins::shortcut_tools`, clashes said in the footer). Listed in Help's sheet and in the palette button's tooltip; a menu entry can't show them (Slint's menu shortcuts are fixed when the window is built).
- **The toolbar's Plugins section** (Mateus, 16 Nov 2026: one section just for plugins): `ToolSpec::toolbar` (a symbol or a short text) puts the tool's button there, after the core's sections; plugins don't make toolbar sections of their own.
- **Folders of a plugin's own** (Mateus, 16 Nov 2026): the manifest's `folders` is a list of names, no longer the two the core knew. Each is beside `plugins` in every OxiGuitar folder: the user's (made at start), the system plugin folders' parents and the program's own folder (`Folders::named`, `named_elsewhere`). `HostRequest::Folder { name }` answers with the user's and the others that exist; `HostRequest::Folders` still answers `soundfonts` and `nam` for the plugins released before.
- **Advice names no plugin** (Mateus, 16 Nov 2026): "can't open any file", "can't play" and "nowhere to send the sound" point at the page of official plugins and no longer name the Guitar Pro, MIDI or audio plugins.
- **Manifests are read from an ELF file's headers alone** (`oxp::elf_section`): `object::File::parse` also read the symbol table and its strings, megabytes in a plugin that isn't stripped, so the manifest speed test (30 manifests in 100 ms, debug build) crept past its budget on CI's ARM64 runner as the test plugin grew (31 ms to 6 ms here). Mach-O and PE files go through `object::File` as before.
- **Not done**: a plugin can't add a mode to the palette (a tool that stays on and takes the next clicks on the page; accepted by Mateus, 16 Nov 2026), or a new kind of thing in the model beyond data and marks on beats (on notes, bars or tracks: the same pattern, when a plugin needs it).

### Interface 1.9 (the core owns nothing of a plugin, ADR 0012)

Mateus, 17 Nov 2026, from oxiguitar-midi#19 (the MIDI plugin's settings window lagged and replayed queued picks): the core owns nothing of a plugin, and settings windows go. A plugin shows its settings in a dialog of its own (1.8), changes a draft there, and saves it in `Tab::closed(true)`; Cancel forgets it. Built:

- **Tools that don't edit the score**: `ToolSpec::edits` (default `true`; `"edits": false` needs 1.9). The window's menus enable such an entry with no score open (`PluginMenuItem::edits`, `ToolRow::edits`), and the worker runs it while the song plays, where every other tool is refused.
- **Settings that changed prepare the sound again**: the host's `SetSettings` compares the new object with the saved one and, when they differ and the save worked, calls `Core::settings_changed(plugin)`; the window's `WindowCore` hands it to the event loop, where `playing::settings_changed` stops the song and prepares the instruments and effects again if that plugin plays any (as the settings window's events did, #143). A plugin that writes its settings only on OK is prepared again once.
- **Retired**: the manifest's `settings_window`, `Plugin::settings_window`, the host's `with_settings_window`, `settings_window` and `settings_event`, the app's `PluginSettingsWindow` and the plugin manager's Settings… button. `Request::SettingsWindow` and `Request::SettingsEvent` are renamed `RetiredSettingsWindow` and `RetiredSettingsEvent` and never sent: they keep their place in the enum, so every later request keeps its encoding and older plugins still load (the SDK answers them "not found"). An older plugin's `settings_window` key is ignored by the host, as any unknown key; the SDK's checks name it as unknown.
- **The test plugin**: the tool `settings` ("Test Settings…", `"edits": false`) opens the dialog `settings` (`SettingsDialog`, the reference for plugins); `interface_1_9_a_plugins_settings_dialog` in the contract tests drives it, Cancel, OK and the window's `settings_changed`.

### Interface 1.10 (the core knows no folder's name, ADR 0012)

Mateus, 17 Nov 2026: interface 1.3's two named shared folders go. `SharedFolder` (`soundfonts`, `nam`) is removed from the interface and the SDK, with `Folders::shared` and the host's `Folders::shared`; `PluginFolders::shared` becomes `retired_shared: Vec<(u32, String)>`, always empty (an enum's index and a `u32` are written alike, so older plugins still read the answer, finding no shared folder there). ### Interface 1.11 (an export's options, #313)

### Interface 1.12 (a performer knows the track's strings, #294)

From #294 (Mateus, 19 Nov 2026: a plugin that plays a fretted track's pitches as a real guitar or True Temperament frets would, chosen per track). `Request::Perform` gave a note's string and key but not the fret, the instrument or the track's choice, so it gains, at its end, `program` (the General MIDI program), `staves` (`PerformStaff { tuning, capo }` by staff; the fret is the key less the open string and the capo) and `settings` (the track's settings for the plugin, `Track::plugins`, as its track section keeps them, 1.3). **Extended in place** (Mateus, 19 Nov 2026): messages are decoded strictly (bytes left over are an error), so a 1.8 to 1.11 performer can't read the longer request; no released plugin performed, so the host asks only manifests of 1.12 or later (`knows_minor(12)`) and the manifest's checks say performing needs 1.12. The test plugin moves to 1.12. Also fixed: the host's cache of each performer's last answer (keyed by the encoded request) is dropped for a plugin whenever it saves changed settings of its own (`HostRequest::SetSettings`), since its answer may follow them; a track's settings are in the request, so they need nothing more.

### Writing a plugin

The plugin developer guide, [`docs/plugins/`](../plugins/src/README.md) (mdBook, published beside the user manual at `/plugin-guide/`), shows how, step by step, from the template plugin in `docs/plugins/template/` (M2's slice 7). The template is a workspace of its own that authors copy: a format (read and write), a tab with widgets and a canvas, score events, settings and a service. It takes the SDK and the contract suite from this repository at the release's tag (git dependencies; nothing is published on crates.io: Mateus, 19 Oct 2026), and its `tests/contract.rs` builds the `.oxp` file and runs the contract suite under `cargo test`. The guide's code examples are included from the template's sources (mdBook anchors), so they are the code CI builds: `scripts/check-plugin-template.sh` copies the template out of the repository, points it at this checkout's SDK, and runs fmt, clippy, its tests, `oxiguitar-plugin-test --build` and `oxiguitar-cli` on its sample, on Linux, Windows and macOS (CI's "Plugin template" jobs, part of `ci-success`).

`plugins/test` remains the example of every part of the interface, and our Guitar Pro plugins (`plugins/gp3` … `plugins/gp`) of a format plugin as we ship it.

### The options considered

| | Native library (chosen) | WebAssembly component (wasmtime) | Both kinds | Separate processes | Scripts (Lua, Rhai) |
| --- | --- | --- | --- | --- | --- |
| One file per plugin | Yes, per target | Yes, one for every target | Yes | One executable per target | Yes |
| Load time | mmap, microseconds; manifest read without loading | Compiling a module takes 10s–100s of ms; cached precompiled copies make later starts fast, at the cost of disk | Both | A process start, milliseconds | Parse at load |
| Speed of DSP (NAM, drums) | Native, full SIMD | Roughly 1.5–3× slower, 128-bit SIMD only | Native where it matters | Native, plus a copy per buffer across processes | Far too slow |
| Can do platform work (audio and MIDI devices, Wayland, macOS) | Yes | No: the host would have to provide every platform API, which puts that code back in the core | Only the native kind | Yes | No |
| Isolation | None: a plugin can crash the app and do anything the user can | Sandboxed: no files or network unless granted | Only the WebAssembly kind | A crashing plugin doesn't take the app down | Partly |
| Size and risk added to the core | A loader of a few hundred lines | wasmtime with its Cranelift compiler, about 10–20 MB and a JIT in the core | Both | IPC framework | An interpreter |
| `unsafe` in our code | Two small modules | None of ours (wasmtime has its own) | Two small modules | None | None |
| iOS | Built in only | Interpreter only (no JIT on iOS) | Built in | Not allowed | Yes |

Native libraries fit Mateus's priorities best: performance, start-up time, platform plugins (which WebAssembly cannot be), and the smallest core. Their costs are a build per target (CI already builds all six), no sandbox (we already decided third-party plugins may do anything, NET-4), and the contained `unsafe` above. If isolation of untrusted third-party plugins ever matters more, WebAssembly can be added later as a second kind for portable plugins, behind the same SDK traits; nothing in this design rules it out.

## What plugins contribute

A manifest lists everything a plugin adds, so the window can show its menu entries, toolbar icons and tabs before its code is loaded.

| Contribution | What it is | Loaded when |
| --- | --- | --- |
| **Format** | Reads and/or writes one file format: name, extensions, and content signatures (bytes at an offset, a ZIP member name; since 1.7 an XML file's first element, or that of a ZIP container's root file) so the core picks it without loading anything (FMT-6). Reading returns a score and its import log (FMT-2); writing returns bytes and a list of what the format loses (FMT-3). | A file of that format is opened or saved |
| **Instrument** (output) | Turns the player's timed events into sound for the tracks given to it: MIDI synthesiser, NAM guitar, RSE, drums. Each track chooses its instrument, with one default for the rest. The manifest says which **instrument classes** it plays (below); without the field it plays everything. | Play is pressed |
| **Service** | One implementation of an interface the core or another plugin defines, so the right code is chosen per platform or environment: an audio device (PipeWire, ALSA, CoreAudio, WASAPI), a MIDI device, Wayland drops. Each declares its conditions; settings can pin a choice; otherwise the first available wins, by priority. | First use |
| **Tool** | A Tools menu entry (interface 1.2): the manifest's `tools` gives its id, name and description; picked, the core asks the plugin to run it, and it changes the score through `Apply` (one undoable command) and answers with a report for the footer. The core's own tools (`oxiguitar-tools`) come first in the menu. | Picked from the menu |
| **Exporter** | File → Export entries: PNG, SVG, WAV (PDF is the core's). Added to the interface when the first exporter plugin needs it. | Picked |
| **Tab** | A tab in the top, bottom, left or right area, with a title (interface 1.1; "Tabs and events" below). Its contents are a tree of standard widgets (buttons, toggles, sliders, lists, text, fields) that the core draws in its own style, plus, if needed, a canvas the plugin draws with OxiGuitar's display list (a fretboard, a meter) and receives pointer events on. Chosen over Slint markup run by Slint's interpreter: no compiler in the core, one look, and it works the same on mobile (Mateus: whatever is fast, easy and elegant, 18 Oct 2026). | The tab is first shown |
| **Toolbar section** | A titled group of icon buttons, toggles and drop-downs in the toolbar. Icons are vector paths in the manifest, tinted by the core. | An item is used |
| **Settings** | A plugin keeps its settings under its id in settings.json and shows them, if it has any, in its own tab. The core draws no settings forms (Mateus, 18 Oct 2026). | |
| **Events** | What the plugin wants to hear about: score opened or changed, selection changed, playback position. Events are pushed to it as they happen; nothing polls. | When the event first fires |

The **player** works like this: the core turns the score into a timeline of events (notes with every effect, tempo, the metronome's clicks and count-in) and runs the transport. Each instrument renders its tracks' events into sample buffers on the audio thread, the core mixes them (volume, pan, mute, solo), and the audio-device service sends the mix to the system. MIDI output to hardware is an instrument that sends MIDI instead of samples. With no instrument installed, the transport is greyed out. The rules of real-time audio (no allocation, no locks, no waiting on the audio thread) bind instrument plugins too, and the SDK's test suite checks them.

### Instrument classes

An instrument plugin declares what it can play, so the player offers it only for tracks it suits; a plugin that says nothing plays everything (Mateus, 18 Oct 2026). The manifest has two optional lists, `plays` and `does_not_play`, of classes from this fixed set, which the core derives from each track's instrument (General MIDI program, percussion flag and strings):

| Class | Tracks |
| --- | --- |
| `fretted` | Guitars and basses with frets, banjo, sitar (GM 24–34, 36, 37, 104, 105; the same set the engraver treats as fretted) |
| `fretless` | Fretless bass and stringed instruments without frets: shamisen, koto (GM 35, 106, 107) |
| `bowed` | Violin, viola, cello, contrabass, string ensembles, fiddle (GM 40–45, 48–51, 110) |
| `keyboard` | Pianos, organs, chromatic percussion such as vibraphone (GM 0–23) |
| `voice` | Choirs and voices (GM 52–54) |
| `winds` | Brass, reeds and pipes, bagpipe, shanai (GM 56–79, 109, 111) |
| `synth` | Synth basses, leads, pads and effects (GM 38, 39, 80–103) |
| `drums` | Percussion tracks (the drum-kit flag, MIDI channel 10) |
| `other` | Harp, timpani, orchestra hit, kalimba, percussive and sound effects (GM 46, 47, 55, 108, 112–127) |

Every one of the 128 programs falls in exactly one class (`oxiguitar_plugin_api::class`, tested).

The `instruments` key is in interface 1.0, but the instrument interface itself comes with the player (M4), in a later minor version. **The player ignores instruments declared by a plugin built for an interface before that one** (Mateus, 19 Oct 2026: the key stays, and the rule avoids rework), so until then no plugin counts as an output.

`plays` lists what the plugin covers (absent = everything); `does_not_play` removes classes from that. A realistic-drums plugin says `plays: ["drums"]`; the MIDI synthesiser says nothing. A track whose chosen instrument no longer exists falls back to the default, with a footer message.

**Plugins can depend on plugins.** A plugin can define a service interface for others, which a plugin that calls it lists under `requires` and treats as optional (a call with no plugin behind it is answered with an error). A plugin that is no use without another lists it under `needs` (interface 1.4, #165), with a lowest version: the NAM plugin needs the MIDI plugin, whose instruments it processes. After every file is examined and each id has its file, the host sets aside a plugin whose need is missing, too old, disabled or itself set aside (`State::Unmet`, repeated until nothing changes), and the footer says so as an error. A plugin renamed or merged into another lists the old ids under `replaces` (interface 1.4): files with those ids count as its older versions, and at the app's start the host copies, once and only where the new id has nothing, the old id's settings.json object and data folder; sidecars' track sections are adopted as each score is read. Nothing old is deleted, so an older OxiGuitar keeps working. The MIDI plugin (`oxiguitar.midi`) replaces `oxiguitar.soundfont` this way.

## Folders and settings

On launch the app makes sure its user folder, `settings.json` (empty, `{}`) and the user plugin folder exist, and creates any that are missing. It never creates or writes system folders; packages install those.

| System | User folder (settings.json) | User plugins | System plugins |
| --- | --- | --- | --- |
| Linux | `$XDG_CONFIG_HOME/oxiguitar/` (default `~/.config/oxiguitar/`) | `$XDG_DATA_HOME/oxiguitar/plugins/` (default `~/.local/share/oxiguitar/plugins/`) | `<bin>/../lib/oxiguitar/plugins/` (covers `/usr/lib`, `/usr/local`, the AppImage and a dev build), then `/usr/lib/oxiguitar/plugins/` and `/usr/local/lib/oxiguitar/plugins/` as fallbacks |
| macOS | `~/Library/Application Support/OxiGuitar/` | `…/OxiGuitar/plugins/` | `OxiGuitar.app/Contents/PlugIns/`, then `/Library/Application Support/OxiGuitar/plugins/` |
| Windows | `%APPDATA%\OxiGuitar\` | `%APPDATA%\OxiGuitar\plugins\` | `plugins\` beside `oxiguitar.exe` (the portable zip), then `C:\Program Files\OxiGuitar\plugins\` as a fallback for installed copies |

- On Linux the folders follow the freedesktop [XDG Base Directory](https://specifications.freedesktop.org/basedir-spec/latest/) convention, like the rest of the desktop (Mateus, 18 Oct 2026): settings under the config home, plugins and their data under the data home. Relative or empty `XDG_*` values are ignored, as the specification says.
- The environment variable `OXIGUITAR_HOME` puts everything in one folder instead (`settings.json`, `plugins/`, `data/`): for tests and for a portable copy on a USB stick.
- `settings.json` key `plugin_folders` (a list of paths) replaces the default list. Folders are searched in order; when two folders hold the same plugin id, the higher version wins, then the build needing more processor features, then the later folder.
- Other keys, written by the core (the plugin manager writes `disabled`): `disabled` (plugin ids), `services` (a pinned implementation per interface, `{"audio-device": "PLUGIN-ID/SERVICE-ID"}`), `instruments` (default and per track), and one object per plugin id for its own settings. Unknown keys are kept as they are. The app and every plugin write through one shared copy, so none overwrites another's keys; a settings.json that couldn't be read at start is never written.
- A plugin that keeps data gets its own folder: `$XDG_DATA_HOME/oxiguitar/data/<plugin id>/` on Linux, `data/<plugin id>/` in the user folder elsewhere. What it can make again (an SF3 set decoded once) goes in its cache folder: `$XDG_CACHE_HOME/oxiguitar/<plugin id>/` (default `~/.cache/oxiguitar/`), `~/Library/Caches/OxiGuitar/<plugin id>/` on macOS, `%LOCALAPPDATA%\OxiGuitar\cache\<plugin id>\` on Windows, `cache/<plugin id>/` under `OXIGUITAR_HOME`. Both are handed over through interface 1.3, with the shared folders (`soundfonts`, `nam`) beside `plugins`.

## The plugin manager

Part of the core, not a plugin (Mateus, 18 Oct 2026; ADR 0008, "Amendments"), so it can't be disabled from its own list. It opens only from **Tools → Plugins**, as a separate, non-modal window, and its only task is to list the plugins and enable or disable them:

- It reads what is in the plugin folders, the user's and the system's (or those `plugin_folders` lists), and nothing else. It never copies, downloads, installs or removes a file. Installing a plugin means putting its `.oxp` file in a plugin folder, by hand or with a package; removing it means deleting the file.
- One row per plugin file found: its name, its version, a tickbox to enable or disable it, its folder, and its state: loaded, not loaded yet (plugins load on first use), replaced by another file of the same plugin, or why it can't be used (damaged, another system's, a newer interface, its conditions don't hold).
- Ticking or unticking writes `disabled` in settings.json and takes effect at the next start, since plugins are never unloaded; the window says so. A file that can't be used for another reason has no tickbox.
- It makes no distinction between our plugins and anyone else's, and neither does the rest of the app (Mateus, 18 Oct 2026): we make promises only about what we distribute, in the README and the manual (NET-4).

Two more things in the core help when a plugin misbehaves: `oxiguitar --safe-mode` starts with no plugins at all (every manifest is still read, so the manager lists every file and can disable one; nothing is loaded, nothing opens, no tab or event), and Help → About lists the plugin folders in search order.

As built in slice 3: `crates/oxiguitar-app/src/manager.rs` (the rows and the `disabled` list, unit-tested without a window) and `ui/plugin_manager.slint`; the host's `Plugins::discover_in_safe_mode` and `start_in_safe_mode`. A tick is refused, saying why, when settings.json couldn't be read at start, since it is then never written.

## Distribution

- **Nothing goes to crates.io** (Mateus, 19 Oct 2026: we write an application, and our code stays on GitHub). Plugin authors take the SDK and the contract suite from this repository at a release's tag, as git dependencies.
- **Our plugins live in this repository**, under `plugins/`, one crate each, so a change to the interface and the plugins that use it land in one pull request while the interface is young. They may move to their own repository once the interface reaches 1.0.
- **Every download carries the basic plugins that work on its system** (Mateus, 27 Oct 2026, replacing the core-only packages and the plugin zips of 18 and 21 Oct: users were confused by two downloads, and one file found on its own, as in the AppImage catalog, opened nothing). Each release attaches one download per system, with SHA256SUMS, and no plugin on its own (0.2.0 and 0.5.0 attached all 25): the Windows zip with the plugins in `plugins\` beside `oxiguitar.exe`, the .dmg with them in the app's `Contents/PlugIns`, the AppImage with them in its own `usr/lib/oxiguitar/plugins`, each the folder the programs search beside themselves (`folders.rs`), so no code changed. Plugins in the user's folder still win a tie of versions; the higher version wins otherwise. The release notes open with a table of the file each system needs (`scripts/package/release-notes.md`). Plugins don't sit in subfolders of a plugin folder: the host reads only `.oxp` files directly in a folder.
- **One AppImage per architecture holds both Linux builds** (Mateus, 27 Oct 2026): the Wayland and the X11 program, each as pure as in its own package (ADR 0009), and an `AppRun` script (`scripts/package/AppRun`) that starts the Wayland one in a Wayland session and the X11 one otherwise. The AppImage catalog tests only X11, so the AppImage keeps an X11 build for as long as we are listed there. Its programs and plugins are built on Ubuntu 22.04, the catalog's test system (glibc 2.35), where the PipeWire plugin doesn't build (cpal 0.18's libspa 0.10 needs newer PipeWire headers than 22.04's 0.3.48): it plays through ALSA, which PipeWire desktops pass on to PipeWire (Mateus, 27 Oct 2026). The .deb and .rpm, built on 24.04, keep the PipeWire plugin. The AppImage also brings the libraries its programs load that aren't on every system nor on the AppImage project's exclude list: xkbcommon's three (libxkbcommon, libxkbcommon-x11, libxcb-xkb; MIT), which the catalog's test system lacks, in `usr/lib/oxiguitar/libs`, found through the programs' RPATH (set only in the AppImage's build), with their copyright files in `usr/share/doc`.
- **Plugin releases from their own repositories** (#165; the workflows and scripts moved to mateusrdp/oxiguitar-packages on 3 Nov 2026, called `@main`, so packaging changes no longer wait for a core tag): `plugin-release.yml` (`workflow_call`) builds a plugin's `.oxp` for the five targets and makes the zips, the `.deb`/`.rpm` (`oxiguitar-NAME`), the per-user Inno Setup installers, the macOS `.pkg` (`enable_currentUserHome`) and `SHA256SUMS`, tests each package, and on a `v*` tag makes a draft release; `plugin-publish.yml` runs on its publication and tells the package repositories, the tap and winget. The scripts are in `scripts/plugin-package/` there; `plugin-release-try.yml` tries all of it on two trial plugins in every pull request that touches them.
- **Two packages on Linux**: `oxiguitar` (or `oxiguitar-x11`), the core, and `oxiguitar-plugins-basic`, the plugins we write and recommend, installed into `/usr/lib/oxiguitar/plugins/`. The core **depends** on the plugins' package of the same version (Mateus, 27 Oct 2026; until then it only suggested it), in the .deb, the .rpm and `debian/`. Both must meet Debian's criteria for its archive. The basic set: the Guitar Pro format plugins (3, 4, 5, 6, 7–8), the MIDI instrument (SoundFont and SFZ) and the audio-device plugins for the system (PipeWire and ALSA on Linux, WASAPI on Windows, Core Audio on macOS), and from v1.0 the NAM plugin; the plugins' package recommends a General MIDI sound set package for the instrument (`fluid-soundfont-gm | musescore-general-soundfont-small` on Debian, `fluid-soundfont-gm` in the .rpm).
- With no plugins found (safe mode, a `plugin_folders` list that leaves the program's folder out, the plugins' package removed), the footer says that nothing can be opened or played and that the basic plugins come with every download.
- The release checks that each download opens a Guitar Pro file with an empty user folder, and that the Linux programs and plugins need no glibc newer than 2.35 (they are built on Ubuntu 22.04, `scripts/package/build-linux.sh`). The release workflow also runs the AppImage catalog's own test on the AppImage (`scripts/package/appimage-catalog-test.sh`).
- Anyone can host plugins anywhere. The core names none: its footer points to our releases page when nothing can be opened or played.

## Testing

- **Each plugin tests itself** as an ordinary Rust library, and **through its file**: tested together in one workspace, Cargo gives every plugin the features of all, so what holds only for a plugin built alone (that it carries and reads only its own format) is checked on its `.oxp` file. The readers' fixture, corpus and fuzz tests stay with the reader code in `oxiguitar-formats`; `oxiguitar-plugin-test`'s `ours` test reads every fixture, reference and corpus file through the five Guitar Pro plugins' files and compares the result with the in-process reader, and the `plugin_dispatch` fuzz target covers the plugins' side of the interface.
- **The interface has a contract suite** (`oxiguitar-plugin-test`) that builds a plugin as an `.oxp` and checks it through the host: the manifest reads without loading, it starts, a contribution it doesn't have is "not found", damaged input (nothing, zeros, its signature alone) and an empty score never crash it, every service answers its probe, every tab's contents can be shown before and after a plausible use of each widget (a click, a tick, the slider's lowest value, an empty field, the first option, a press, drag and release on a canvas), and every kind of event it subscribes to is taken without an error. The instrument checks (nothing allocated, locked or waited for on the audio thread) come with the instrument interface (M4). The test plugin (`plugins/test`) runs every part of the interface end to end: reading and writing with their logs, errors with offsets, a caught panic, the choice of services (conditions, priority, probe, a pin), instruments by class, settings, footer messages, a plugin calling a service through the host, duplicates, disabled and damaged files, and (1.1) two tabs in two areas with every kind of widget and a canvas, pointer events in canvas units, contents the core refuses, events in order and merged, a redraw asked for after an event, and the open score asked for. The `plugin_tab` fuzz target covers a plugin's answer with a tab's contents as the core takes it, canvases drawn.
- **The core is tested with no plugins** (it opens nothing and says why), with test plugins, and with ours.
- The existing gates stay: the speed budget now includes reading the manifests and loading the format plugin (target: the 300-bar file still opens in under a second, and start-up with 30 plugins installed costs under 10 ms of manifest reading); visual references must not change when the readers move into plugins; NET-5 runs with our plugins installed.
- CI path filters build and test only the plugins a pull request touches, plus the contract suite.

## Crashes

A plugin runs in OxiGuitar's process and may crash it (Mateus, 16 Nov 2026: acceptable and fair, as long as the user can tell which plugin it was and has something useful to send). `oxiguitar-host/src/crash.rs`:

- Every call into a plugin library (its initialisers and start, each request, each render and process call, `allocations`) marks the calling thread with the plugin (`Slot::running`, a thread-local, put back when the call returns, so nested calls unwind right).
- On Linux each plugin's loaded segments are noted (`dl_iterate_phdr`), so a crash in a plugin's code is named on any thread, its own threads included, with the offset in its file for `addr2line`.
- `install` (the app's start, in `begin`) sets a handler for SIGSEGV, SIGBUS, SIGILL, SIGFPE and SIGABRT (Linux, macOS; `SA_ONSTACK`) or the unhandled-exception filter (Windows). The handler writes `crash/last-crash.txt` in the data folder and the same lines to stderr, without allocating (descriptions prepared at load in tables of atomics, the text put together in static space, since the alternate signal stack is too small for a 4 KB buffer in a debug build), then puts the previous action back and lets the crash go on (Rust's stack-overflow message included).
- `last` reads the report at the next start, renames it `crash-SECONDS.txt`, and the window shows it as the core's advice (`Report::advice`), with the plugin's homepage as a link.
- The contract suite crashes the test plugin in a child process, on the calling thread and on a thread of its own, and checks the report.

## Privacy and trust

NET-1 to NET-5 cover the core and our plugins. A native plugin can do anything the user can, so the README and the manual say plainly that the promises cover only the app and the plugins we publish (NET-4). The app itself makes no distinction between our plugins and others' (Mateus, 18 Oct 2026). Our plugins download only when the user asks, through the core's consent dialog.

## Debian

Goal (Mateus, 18 Oct 2026): `oxiguitar` and `oxiguitar-plugins-basic` hosted in Debian's own archive, in **main**, as MuseScore and TuxGuitar are (TuxGuitar is in unstable as `1.6.6+dfsg1-3`). Main is the right area: everything we use is DFSG-free. Debian's other areas don't help with what is hard here: **non-free** is for software whose *licence* isn't free and **contrib** for free software that needs non-free software, while our obstacle is packaging work, not licences.

What Debian's archive needs, and where we stand:

| Need | Where we stand | Work |
| --- | --- | --- |
| DFSG-free licences for every file | Yes: GPL-3.0, MIT, Apache-2.0, OFL-1.1 and the like, enforced by cargo-deny | Keep it; a `debian/copyright` listing every crate's licence, generated like THIRD-PARTY-LICENSES.html |
| Build from source with Debian's own tools, offline | Builds need no network. Our minimum Rust (1.99) comes from rustup since 24 Oct 2026 (Mateus) and is ahead of Debian unstable's rustc (1.97.1; 1.98 in experimental): the archive build waits for unstable to reach it, so it is raised only when needed | A `debian/` directory (debhelper and `dh-cargo`) building both packages; a CI job building it in a Debian sid container with the network off |
| **Every Rust crate we use packaged in Debian** (`librust-*-dev`), at versions Debian has, or a justified copy in our source | The hard part. Slint is in unstable at the latest upstream release (Mateus, 17 Nov 2026) | An audit of every crate in `Cargo.lock` against Debian; package the missing ones with the Debian Rust team (its `debcargo` tooling), or narrow our dependencies |
| No copies of things Debian already ships | We bundle Bravura and Noto Sans | Use `fonts-noto-core` instead of our Noto copy in the Debian build; Bravura has no Debian package we found, so we package it (with its sources) or ship it with its OFL licence |
| Debian Policy and a lintian-clean package | Paths follow the FHS (`/usr/bin`, `/usr/lib/oxiguitar/plugins`) | Manual pages for `oxiguitar` and `oxiguitar-cli`; lintian in CI |
| A Maintainer with a working email, and a Debian Developer to sponsor uploads | Our own .deb names the GitHub issue tracker (by decision); Debian requires an email address of a person or a team there | Find a sponsor (mentors.debian.net, a request for sponsorship, or a team such as Debian Multimedia); the Maintainer becomes that team's list or a project address, not Mateus's own email |

Our GitHub release .deb can keep shipping in the meantime; the Debian archive's packages would be built from the same source by Debian.

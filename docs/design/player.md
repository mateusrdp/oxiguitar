# The player (M4)

How OxiGuitar plays a score: what the core does, what plugins do, which libraries do the work, and how the sound stays exactly on what the cursor shows. **Status: approved by Mateus on 25 Oct 2026** (proposed 21 Oct; his answers below), with the NAM plugin moved into v1.0. The measurements behind it are in "The spike" below; the code is `spikes/audio/` and `spikes/nam-bench/`.

## What matters most

People play along with OxiGuitar, as with a backing track. So (Mateus, 21 Oct 2026):

- **The sound is exactly what the cursor shows, for exactly the written duration.** Every note starts on the sample the score puts it on and stops on the sample it ends; the cursor shows the beat being heard, not the beat being computed; nothing drifts, however long the song.
- **Nothing stutters.** The audio thread never waits: it allocates no memory, takes no locks and makes no system calls (the brief's rule), and everything it needs is loaded and in memory before Play.
- **It plays out of the box.** With nothing installed beyond OxiGuitar and its basic plugins, it plays with the sound set the system already has. Better sounds are files the user places in a folder; OxiGuitar downloads nothing (Mateus, 21 Oct 2026, replacing PLAY-8's download button). Whenever it plays with a system's basic set, the footer says so and links to the manual's page on getting better sounds.
- **The best sound we can get**, since this signal later feeds NAM: the better the source, the better the modelled guitar. Quality comes before disk size.

## The chain

```
 score ──► TIMELINE (core) ──► SCHEDULER (core, audio thread) ──► INSTRUMENT per track (plugin)
           every event at its                                      SoundFont plugin: SF2, SF3, DLS
           sample, tempo map,                                      (rustysynth), SFZ (our sampler)
           repeats, feel, count-in,                                         │ a buffer per track
           metronome                                                        ▼
                                                                   EFFECTS per track (plugin, M7:
                                                                   NAM + cabinet IR on guitars)
                                                                            │
 cursor ◄── AUDIO CLOCK (core) ◄── AUDIO DEVICE (plugin, cpal) ◄── MIXER (core: volume, pan,
           samples played,         PipeWire, ALSA, WASAPI,         mute, solo, metronome)
           minus latency           CoreAudio
```

- **The timeline (core, off the audio thread).** The score becomes a list of events, each at an exact sample: notes with their string, fret, pitch, velocity, length and every effect (bend curves, slides, vibrato, palm mute, harmonics, dead and ghost notes, let ring, tremolo picking, trills, grace notes, strokes), tempo changes, repeats and jumps in playing order, swing and triplet feel, the count-in and the metronome's clicks. It also keeps the map back from sample to beat, for the cursor. It is built when a file opens and updated where an edit touches, so Play never waits for it. Golden-file tests cover it (the milestone's gate).
- **The scheduler (core, audio thread).** Each device callback, it hands every instrument the events that fall in the callback, split at their samples, from queues filled ahead (lock-free, single producer and consumer). Loop, speed (25 to 200 %, by re-timing the events, so the pitch never changes) and seeking are messages on the same queues.
- **Instruments (plugins).** An instrument renders the tracks given to it, each into its own buffer, from events that carry the notes' meaning rather than MIDI: a SoundFont instrument turns them into MIDI-like control (one channel per string, so a bend moves one string; programs for palm mute, harmonics and dead notes where the set has them), with a helper in the SDK every instrument can share; an SFZ instrument can pick articulations from them; M7's guitar takes them as they are.
- **Effects (plugins, M7).** After the instrument, each track can pass through a chain of effects, such as NAM and a cabinet impulse response on a guitar track. The interface for it comes with M7, but M4 already renders each track apart so that it can be inserted without rework.
- **The mixer (core).** Volume, pan, mute and solo per track (the Tracks rows), the metronome, the master level.
- **Audio devices (plugins).** One per system's audio API, each built with only its own code (ADR 0008, "no dead code"): PipeWire and ALSA on Linux, WASAPI on Windows, CoreAudio on macOS, all through cpal. The stream opens at 48 kHz, NAM's rate, which PipeWire, WASAPI and CoreAudio convert themselves when the hardware runs at another; where a device refuses 48 kHz, the core converts.

## Staying in sync

- **One clock: the audio device's.** The core counts the samples it has handed the device. The sample being heard is that count minus the device's delay to the speaker (cpal reports, for every callback, when its first sample will be played) minus the latency the instruments and effects declare (a resampler's, an oversampler's; NAM adds none). The cursor shows the beat at that sample, through the timeline's map. No timer and no wall clock decide where the music is.
- **The cursor moves on every frame the window draws while playing**, computed afresh from the audio clock each time, so it never drifts and never runs ahead. It can't be finer than the screen (16.7 ms at 60 Hz), but the sound is sample-exact. When nothing plays, nothing runs: no polling.
- **Notes start on their sample.** The core splits every callback at each event. SoundFont synthesisers render in blocks and start a note at the next block boundary: rustysynth runs with blocks of 8 samples, so a note starts at most 7 samples (0.15 ms) late, measured, against up to 63 samples (1.3 ms) with 64, OxiSynth's fixed size (which a fork would change). Our SFZ sampler starts notes on their exact sample. Every note's length comes from the timeline, so durations are exact too.
- **No stutter.** Sounds are loaded when a file opens (or when its sounds change), not on Play, and their memory is touched page by page then, so the audio thread never waits for the disk or a page fault. The contract suite fails an instrument that allocates, locks or waits during rendering. Playback starts within 100 ms (the milestone's gate).

## The engine, as built

Built in slice 2, second pull request (`oxiguitar-play`'s `schedule` and `engine`; interface 1.3's `realtime`). Where it differs from the plan above, this is what holds:

- **No feeder thread.** The plan had the audio thread read queues a thread fills ahead; refilling them would need waking that thread (a system call on the audio thread) or polling. Instead the timeline becomes a `Schedule` off the audio thread (every note in the plugins' form, sorted by start and by end, routed to its source, with the clicks), handed to the engine whole, and the audio thread reads it directly: a cursor into each list, a binary search on a seek. Lock-free single-producer queues (rtrb, MIT OR Apache-2.0) carry the window's commands in (play, pause, seek, loop, speed, the mixer, the metronome, a new schedule or new sources) and carry back what the engine lets go of (an old schedule, old sources), which the window drops, and the song's end. A new schedule or new sources are taken only while nothing plays (no editing while playing).
- **Time.** The engine keeps an anchor: a device frame, the score's time there, and the score's seconds per frame (the speed over the rate), reset only on play, seek, loop and speed changes. A frame's time is the anchor's plus the frames since times the step: nothing accumulates, so nothing drifts. An event at time `t` happens on the first frame whose time is at or after `t`. Each device callback is split at every event (and at the engine's largest piece); the events of a piece happen on its first frame, and a piece may have events and no frames.
- **Notes cross by value** (`RtNote`: id, track slot, key, velocity, string, sound, harmonic, attack, flags, start and end in score seconds), with their pitch curves as runs of one shared array of points that stays put while anything sounds. No pointer is held across calls.
- **Sources render all the time**, even stopped and during the count-in, so a note let go of fades out as its sound set says instead of being cut. Gains ramp over a piece when the mixer changes (no zipper noise), and the first piece takes them at once, so a note's first frame is never silent. Pan is constant-power.
- **Loops** jump on the frame of their end, with "all off" first; **the count-in** plays the timeline's count-in clicks before the start point, then the music; **the metronome** is a short sine (higher on the bar's first beat) the core synthesises, so it needs no sound set.
- **The clock.** After each callback the engine publishes, through a sequence lock the audio thread never waits on, the device frames handed over at the callback's start, when it started, the delay to the speaker plus the sources' largest latency, and its latest pieces of played time. `Control::heard` extrapolates from the callback's start to now (at most a second), takes the delay off, and maps the frame back to the score's time through those pieces, so a loop or a seek moves the cursor exactly when the sound moves. Lining up sources of different latencies comes with the first source that has any (ours have none).
- **Sample rate.** Streams ask for 48 kHz; where a device refuses, the engine runs at the device's rate (instruments are told the rate when prepared). Converting to 48 kHz for an effect that needs it (NAM) comes with slice 5.
- **Gates** (`oxiguitar-play/tests/engine.rs`, against a stand-in device with callbacks of 1 to 1024 frames): every note starts and ends on its frame at 25, 100 and 200 %, and the sound starts on the first note's frame; loops and seeks land on their frames; the count-in comes first; ten minutes of notes end on their frames and the clock maps every device frame to its time exactly; volume, pan, mute, solo and the metronome. `tests/engine_allocations.rs`: nothing is allocated while playing, with a loop, the count-in and the metronome. The contract suite plays the test plugin's sine through the engine and finds the first note's first frame where it belongs.
- **The contract suite's real-time checks**: each instrument and effect is prepared and played a short script; a note must start within the instrument's declared resolution and not before; the SDK's counting allocator (every `.oxp` built with `export_plugin!` has it) must count nothing while it renders; and on Linux the renders run in a forked copy of the test behind a seccomp filter that traps every system call. A test plugin that misbehaves on purpose shows each check failing.

## Sounds

- **Sound sets are files in a folder, like plugins.** A `soundfonts` folder sits beside `plugins` in the user's folder: `~/.local/share/oxiguitar/soundfonts/` on Linux, `%APPDATA%\OxiGuitar\soundfonts\` on Windows, `~/Library/Application Support/OxiGuitar/soundfonts/` on macOS, `soundfonts/` in `OXIGUITAR_HOME`. OxiGuitar creates it at start, as it does `plugins`. Put an `.sf2`, `.sf3` or `.dls` file in it, or an SFZ instrument's folder (its `.sfz` files with their samples); nothing else is needed.
- **The system's own sets are read too**, never written: on Linux `/usr/share/sounds/sf2`, `/usr/share/sounds/sf3` and `/usr/share/soundfonts` (FluidR3, MuseScore General, TimGM6mb and others from the distribution's packages); on Windows `C:\Windows\System32\drivers\gm.dls`, the General MIDI set every Windows has; on macOS the General MIDI set in CoreAudio (`gs_instruments.dls`). So it plays out of the box everywhere. The `oxiguitar-plugins-basic` .deb and .rpm **recommend** a General MIDI sound set package (`fluid-soundfont-gm` or `musescore-general-soundfont-small` on Debian and Ubuntu; `fluid-soundfont-gm` on Fedora), which the package manager installs unless told not to.
- **Choosing.** The sound plugin's settings window (opened from the plugin manager: Tools → Plugins…, the plugin's Settings…) lists every set found, with its folder, and picks one for guitars, one for basses, one for drums and one for everything else. The choice is global, for every file (Mateus, 21 Oct 2026). Until the user picks, the best set found is used: a set in the user's folder before the system's, the larger before the smaller.
- **The way to better sound is always in sight.** Whenever playback uses only a system's basic set, the footer says once, as a warning, that better sounds can be installed, with a link to the manual's "Better sounds" page, which says what to get, where from, its licence and size, and where to put it, by instrument (guitars, basses, drums), with the DI guitar set for NAM.
- **What we recommend** (kept in `claude/sound-research.md` and the manual; all free to use; none bundled): MuseScore General and FluidR3 (MIT) for everything; FreePats' guitars (CC0, with a raw DI bank), Karoryfer's Black and Green Guitars and Shinyguitar (CC0); Karoryfer's basses (CC0); SM Drums (public domain), Naked Drums (CC BY 4.0), Karoryfer's drums (CC0). Before the manual names them, Mateus listens to renders of the reference songs with each.

## Libraries

| Job | Choice | Why |
| --- | --- | --- |
| SF2 synthesis | **rustysynth** 1.3.8 (MIT, no dependencies; decided by Mateus, 25 Oct 2026): the better supported (14 commits in 2026, releases 1 and 20 Oct 2026, outside pull requests merged within days). Its gaps against OxiSynth and FluidSynth: linear sample interpolation (the top octave −2.5 dB, some aliasing: by ear "a tad less natural") and no custom modulators (every General MIDI set defines them: FluidR3 746, MuseScore General 2486). We write both, fourth-order interpolation (seventh as an option) and file modulators, as FluidSynth defines them, and offer them upstream; until a rustysynth release has them, the SoundFont plugin builds from our fork through Cargo's `[patch]`, which goes when upstream releases. OxiSynth (LGPL-2.1, FluidSynth's design, dormant) stays the reference for both. |
| SF3 | rustysynth, after decoding the Ogg Vorbis samples into an in-memory SF2 (lewton, MIT OR Apache-2.0) | Measured: MuseScore General Lite (40 MB) becomes a 216 MB SF2 in 6 s on one slow core, done when the set is first loaded, in parallel on real machines, and plays like FluidSynth's render of the .sf3. |
| DLS (Windows, macOS) | Our reader, turning DLS into an in-memory SF2 for rustysynth (DLS articulations map to SF2 generators; FluidSynth 2.5's DLS loader, LGPL, is the reference) | So both play out of the box. Checked on GitHub's Windows and macOS runners, which have the sets. |
| SFZ | **Our own sampler** | No Rust SFZ engine fits: xsynth (LGPL-3.0) leaves out modulation envelopes and LFOs, sofiza is a parser from 2022. The best free guitars, basses and drums are SFZ: round robins, velocity layers, release samples, key switches, choke groups. WAV (hound), FLAC (claxon) and Ogg (lewton) samples. Sample-exact starts. |
| Audio devices | **cpal** 0.18 (Apache-2.0; Debian packages cpal, lewton and hound) | Every system's API, PipeWire included; reports when each buffer will be heard. Measured: rendering three tracks inside its callback, no allocation. |
| NAM (M7) | Decided in M7 after the speed test on every system (the brief's rule); see "NAM" below | |

All of them speak plain `f32` sample buffers, planar or interleaved: the synthesiser fills a track's left and right buffers, NAM processes a mono buffer in place, cpal takes interleaved frames. They fit without conversion beyond copying, and the spike runs the whole chain in 64-sample callbacks with no allocation.

## NAM (for M7)

Two pure-Rust engines exist, both run NAM's `.nam` files, both allocation-free on the audio thread (measured for nam-rs):

- **nam-rs** 0.4.0 (MIT; serde, serde_json, thiserror): WaveNet A1 and A2, LSTM, slimmable models; plain Rust, so it builds for every target we ship. NAM's standard WaveNet at 2.6–4.9× real time on one core of GitHub's runners (Linux and Windows on x86_64 and ARM64, an M1), median 240–520 µs per 64 samples.
- **NeuralAmpModeler-rs** 1.0.1 (Apache-2.0): hand-written AVX2 and AVX-512 kernels, cabinet IR convolution, resampling, oversampling, a noise gate. **About ten times faster**: the standard WaveNet at 25× real time (median 52 µs per 64 samples on an AMD EPYC 7763), the same model's output as nam-rs within 6e-6 (both match NAM's reference). But it builds only for **Linux on x86_64** with the x86-64-v3 baseline (AVX2, FMA: Intel from 2013, AMD from 2015): besides refusing other processors, its memory code is Linux's and glibc's throughout (`memfd_create`, huge pages, mirrored ring buffers, `__errno_location`, pinned glibc symbols), so it doesn't build for Windows (seen on GitHub's runner) or for macOS. It needs Rust 1.99 (we moved to it, 24 Oct 2026). Several releases this month were yanked.

**Decided (Mateus, 25 Oct 2026): NeuralAmpModeler-rs on Linux x86_64, nam-rs everywhere else**, and the NAM plugin ships in v1.0 (the spike showed the approach works). The sound is the same everywhere, since both match NAM's reference and each other to under 1e-5; only the cost per track differs. If NeuralAmpModeler-rs gains Windows or macOS later, those builds switch too. The plugin's manifest needs a condition on the processor's features, so that an x86_64 machine without AVX2 gets the nam-rs build instead of crashing. The guitar signal for NAM: a DI sound set (FreePats' Direct bank, CC0) through the SoundFont plugin; the brief's plucked-string model stays for M7.

Per-track NAM settings (whether to use NAM, which model and impulse response, input and output level) belong in the track dialog, added by the NAM plugin only when it is installed (Mateus, 21 Oct 2026): interface 1.3 gives plugins sections of the track dialog. Cabinet IRs we could ship: Guitarix's BestPlugins pack (GPL-2.0-or-later). Amp captures: users bring their own, as the brief says; ones we'd ship need a licence that allows it.

## The plugin interface (1.3)

Additions only, at the ends of enums, as every minor version (frozen with the release that brings them):

- **Instruments.** The manifest's `instruments` key (in 1.0) comes alive; the SDK's `Instrument` trait: `prepare` (off the audio thread: the tracks it plays, the sample rate, the largest callback; load what they need), `render` (on the audio thread: this callback's events per track, into a buffer per track), `latency`. Instruments declared by a plugin built for an interface before 1.3 are ignored (Mateus, 19 Oct 2026).
- **Audio devices**, as services (`audio-device`): open a stream at a rate and callback size, call the host's render function from the device's callback with the delay to the speaker, report errors and device changes. The host picks the first available by priority, or the one settings.json pins.
- **A settings window per plugin**, opened from the plugin manager's Settings… for plugins whose manifest asks for one, built from the same widgets as a plugin's tab (1.1), its values kept in the plugin's own part of settings.json.
- **Footer messages with a link**, opened in the system's browser when clicked.
- **Effects**: a plugin can process a track's buffer after its instrument (manifest `effects`, SDK trait `Effect`: `prepare` off the audio thread, `process` on it, `latency`), per track, in the order the track lists them; the NAM plugin is the first.
- **Sections of the track dialog**: a plugin adds its own rows to the track dialog (the widgets of a tab, 1.1), kept per track in the score's settings for that plugin; without the plugin they don't show. Saved beside the score in `FILE.oxg` (`song.gp3.oxg`; Mateus, 25 Oct 2026), since no score format holds them; built (plugins.md, "Interface 1.3").
- **The plugin's own folders**: its data folder (brief: "The plugin's own data folder", in the wishlist) and the sound-set folders, handed over by the host.
- The contract suite checks every instrument for allocations, locks and waits while rendering, and that it keeps time (a note asked for at a sample starts there, within the instrument's declared resolution).

## Slices

Each slice is one or more pull requests into develop with every gate green, a test build on its branch and direct artifact links (with their expiry) for Mateus.

1. **The timeline** (core, no window): the score as events at their samples, playing order with repeats, jumps and endings, tempo changes, feel, count-in and metronome; the map from sample back to beat; every TAB-1 effect as a note event (PLAY-3, PLAY-4). Gates: golden files over the fixtures and the corpus (`oxiguitar-cli events FILE`), and the timeline of the 300-bar song built well within the 100 ms start budget. **Built 25 Oct 2026** (`crates/oxiguitar-play`). As built: times in seconds at 100 % speed (the scheduler turns them into samples at the device's rate and the chosen speed); a bar that doesn't add up lasts as long as its longest voice when that is longer than its time signature, so no note is cut; after a D.C. or D.S. repeats play once and endings take their last; a closing repeat without an opening one goes back to the bar after the previous closing repeat; a grace note before the song's very first beat plays on the beat (there is no time before it); natural harmonics sound at the fret's harmonic (12th an octave, 7th and 19th an octave and a fifth, 5th two octaves, 4th, 9th and 16th two octaves and a third), pinch harmonics an octave and a fifth up.
2. **Interface 1.3, audio devices and the engine** (core): the scheduler, mixer and audio clock; the four audio-device plugins; the test plugin's instrument (a sine per note) through the contract suite's real-time checks; settings windows, footer links and the plugins' folders. Three pull requests: (1) the interface off the audio thread: settings windows, track-dialog sections, footer links, folders (built 25 Oct 2026); (2) the engine, tested offline against a stand-in device; (3) the audio-device plugins and `oxiguitar-cli play`. Mateus's answers (25 Oct 2026): cpal is used as it is, so the PipeWire plugin carries cpal's ALSA code too (cpal always builds it on Linux), an accepted exception to "only its own code"; track sections are saved in `FILE.oxg`; **no editing while playing** (edits are refused while the sound runs and allowed when paused, so the engine never swaps a timeline under sounding notes); `oxiguitar-cli play` stays, with its man page.
3. **The SoundFont plugin**: SF2, SF3 and DLS through the synthesiser chosen above, starting notes within 0.15 ms of their sample; the `soundfonts` folders and the system's; its settings window (a set for guitars, basses, drums and the rest); the effects in MIDI terms (PLAY-3). Windows and macOS play out of the box, checked on their CI runners; the .deb and .rpm recommend a sound set package.
4. **The window**: the transport in the top area (play, play selection, pause, stop, rewind, loop a selection, count-in, metronome, visual metronome, speed 25–200 %; PLAY-5), the cursor following playback and scrolling the page, the mixer in each Tracks row (PLAY-6), the footer's warning and link, the manual's Playback and Better sounds pages. **Then a release for testers** (v0.9, Mateus to decide), as soon as it plays reliably.
5. **The NAM plugin** (in v1.0, Mateus, 25 Oct 2026): effects and track-dialog sections in the interface; NeuralAmpModeler-rs on Linux x86_64 (built with `target-cpu=x86-64-v3`, with a processor-features condition) and nam-rs everywhere else; cabinet impulse responses (its convolution engine on Linux x86_64, ours elsewhere); the track dialog's NAM section (on or off, model, impulse response, input and output level); models and impulse responses from a `nam` folder beside `soundfonts`, as files the user puts there; the manual's page on getting a DI set, models and impulse responses. Cabinet IRs we may ship: Guitarix's BestPlugins pack (GPL-2.0-or-later).
6. **The SFZ sampler**, in the SoundFont plugin, tested on the recommended guitars, basses and drums. If it proves a big job, it goes to v1.1 (Mateus, 21 Oct 2026).
7. **WAV export** (PLAY-7, an export plugin), the milestone's gates (playback matches the written effects by ear on the reference songs; in sync over 10 minutes; practice tools on every reference song), then v1.0.

## The spike

`spikes/audio/` and `spikes/nam-bench/` (spikes/README.md says how to run them). Measured on the session's virtual machine (2 cores of a 2.8 GHz Xeon, shared), 21 Oct 2026; the spikes workflow repeats them on every target.

- **Synthesisers**, a four-bar song with guitar (six channels, a bend), bass and drums, one synthesiser per track, 64-sample callbacks split at every event, 48 kHz:

  | Set | rustysynth (64) | OxiSynth | Closeness to FluidSynth's render (envelope correlation; spectral distance) |
  | --- | --- | --- | --- |
  | TimGM6mb (6 MB) | 244× real time, load 5 ms | 255×, 55 ms | rustysynth 0.992, 2.2 dB; OxiSynth 0.996, 2.2 dB |
  | FluidR3_GM (148 MB) | 155×, 105 ms | 104×, 898 ms | rustysynth 0.994, 2.3 dB; OxiSynth 0.997, 1.6 dB |
  | MuseScore General Lite (SF3, 40 MB) | 163× (+6 s decoding) | 146× (+6 s) | rustysynth 0.991, 2.1 dB; OxiSynth 0.997, 0.3 dB |
  | GeneralUser GS 2.0.3 (32 MB) | 253×, 27 ms | 191×, 340 ms | rustysynth 0.996, 2.1 dB; OxiSynth 0.996, 1.9 dB |

  No allocation in either while playing. rustysynth with blocks of 16 runs at 115×, with 8 at 83–119×.
- **Timing**: a note asked for n samples into a render starts up to `block − 1` samples late (rustysynth 64: up to 63; 32: 31; 16: 15; 8: 7; OxiSynth: 63).
- **NAM** (nam-rs, 64-sample blocks, mono 48 kHz): LSTM example 75–85× real time; NAM's standard WaveNet 2.0–2.2× (median 590 µs of the 1333 µs a block lasts). No allocation.
- **The whole chain** (three tracks through rustysynth, the guitar through NAM, mixed, interleaved), 64-sample callbacks: with the LSTM model, median 28 µs, 99th percentile 64 µs; with the standard WaveNet, median 592 µs, 99th percentile 1303 µs, which leaves no margin on this machine. No allocation.
- **A live device** (cpal, ALSA's null device here): the song rendered inside the device's callbacks of 240 frames, worst 406 µs of 5000, no allocation.
- **SF3**: decoding MuseScore General Lite's 1254 Ogg samples takes 6 s on one core (4 s on GitHub's ARM64 runner), Full's 2202 samples 12 s; MuseScore's files leave odd chunks unpadded, which the reader allows for. Decoded once, the plugin keeps the SF2 in its data folder so later starts load it directly.
- **Round 2** (24 Oct 2026): MuseScore General Full, as SF3 (86 MB) and lossless SF2 (490 MB), through all three: OxiSynth matches FluidSynth to 0.3 dB, rustysynth 2.4 dB away (−2.5 dB at 8–16 kHz, its linear interpolation). Mateus's ears: the sets differ far more than the synthesisers; FluidR3 best, MuseScore close.
- **Across GitHub's runners** (21 Oct 2026): rustysynth 170–300× real time for three tracks, OxiSynth 140–255×, no allocation anywhere; Windows and macOS have their DLS sets (gm.dls: 3.4 MB, 235 instruments; gs_instruments.dls: 2.0 MB, 235 instruments) where the spike looks for them; the whole chain with NAM's standard WaveNet through nam-rs runs at a median 500 µs per 64-sample callback, 540 µs at the 99th percentile.

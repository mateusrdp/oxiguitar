# The player (M4)

How OxiGuitar plays a score: what the core does, what plugins do, which libraries do the work, and how the sound stays exactly on what the cursor shows. **Status: approved by Mateus on 25 Oct 2026** (proposed 21 Oct; his answers below), with the NAM plugin moved into v1.0. The measurements behind it are in "The spike" below; the code is `spikes/audio/` and `spikes/nam-bench/`.

## What matters most

People play along with OxiGuitar, as with a backing track. So (Mateus, 21 Oct 2026):

- **The sound is exactly what the cursor shows, for exactly the written duration.** Every note starts on the sample the score puts it on and stops on the sample it ends; the cursor shows the beat being heard, not the beat being computed; nothing drifts, however long the song.
- **Nothing stutters.** The audio thread never waits: it allocates no memory, takes no locks and makes no system calls (the brief's rule), and everything it needs is loaded and in memory before Play.
- **It plays out of the box.** With nothing installed beyond OxiGuitar and its basic plugins, it plays with the sound set the system already has. Better sounds are files the user places in a folder; OxiGuitar downloads nothing (Mateus, 21 Oct 2026, replacing PLAY-8's download button). The first time it plays with only the system's sets, the footer says so, once, and links to the manual's page on getting better sounds.
- **The best sound we can get**, since this signal later feeds NAM: the better the source, the better the modelled guitar. Quality comes before disk size.

## The chain

```
 score ──► TIMELINE (core) ──► SCHEDULER (core, audio thread) ──► INSTRUMENT per track (plugin)
           every event at its                                      SoundFont plugin: SF2, SF3, DLS
           sample, tempo map,                                      (rustysynth), SFZ (our sampler)
           repeats, feel, count-in,                                         │ a buffer per track
           metronome                                                        ▼
                                                                   EFFECTS per track (plugin, M7:
                                                                   NAM + cabinet IR on guitars)
                                                                            │
 cursor ◄── AUDIO CLOCK (core) ◄── AUDIO DEVICE (plugin, cpal) ◄── MIXER (core: volume, pan,
           samples played,         PipeWire, ALSA, WASAPI,         mute, solo, metronome)
           minus latency           CoreAudio
```

- **The timeline (core, off the audio thread).** The score becomes a list of events, each at an exact sample: notes with their string, fret, pitch, velocity, length and every effect (bend curves, slides, vibrato, palm mute, harmonics, dead and ghost notes, let ring, tremolo picking, trills, grace notes, strokes), tempo changes, repeats and jumps in playing order, swing and triplet feel, the count-in and the metronome's clicks. It also keeps the map back from sample to beat, for the cursor. It is built when a file opens and updated where an edit touches, so Play never waits for it. Golden-file tests cover it (the milestone's gate).
- **The scheduler (core, audio thread).** Each device callback, it hands every instrument the events that fall in the callback, split at their samples, from queues filled ahead (lock-free, single producer and consumer). Loop, speed (25 to 200 %, by re-timing the events, so the pitch never changes) and seeking are messages on the same queues.
- **Instruments (plugins).** An instrument renders the tracks given to it, each into its own buffer, from events that carry the notes' meaning rather than MIDI: a SoundFont instrument turns them into MIDI-like control (one channel per string, so a bend moves one string; programs for palm mute, harmonics and dead notes where the set has them), with a helper in the SDK every instrument can share; an SFZ instrument can pick articulations from them; M7's guitar takes them as they are.
- **Effects (plugins, M7).** After the instrument, each track can pass through a chain of effects, such as NAM and a cabinet impulse response on a guitar track. The interface for it comes with M7, but M4 already renders each track apart so that it can be inserted without rework.
- **The mixer (core).** Volume, pan, mute and solo per track (the Tracks rows), the metronome, the master level.
- **Audio devices (plugins).** One per system's audio API, each built only for its system (ADR 0008, "no dead code"; cpal's ALSA host rides along in the PipeWire plugin, accepted on 25 Oct 2026): PipeWire and ALSA on Linux, WASAPI on Windows, CoreAudio on macOS, all through cpal. The stream opens at 48 kHz, NAM's rate, which PipeWire, WASAPI and CoreAudio convert themselves when the hardware runs at another; where a device refuses 48 kHz, the engine runs at the device's rate (converting for NAM comes with slice 6).

## Staying in sync

- **One clock: the audio device's.** The core counts the samples it has handed the device. The sample being heard is that count minus the device's delay to the speaker (cpal reports, for every callback, when its first sample will be played) minus the latency the instruments and effects declare (a resampler's, an oversampler's; NAM adds none). The cursor shows the beat at that sample, through the timeline's map. No timer and no wall clock decide where the music is.
- **The cursor moves on every frame the window draws while playing**, computed afresh from the audio clock each time, so it never drifts and never runs ahead. It can't be finer than the screen (16.7 ms at 60 Hz), but the sound is sample-exact. When nothing plays, nothing runs: no polling.
- **Notes start on their sample.** The core splits every callback at each event. SoundFont synthesisers render in blocks and start a note at the next block boundary: rustysynth runs with blocks of 8 samples, so a note starts at most 7 samples (0.15 ms) late, measured, against up to 63 samples (1.3 ms) with 64, OxiSynth's fixed size. Our SFZ sampler starts notes on their exact sample. Every note's length comes from the timeline, so durations are exact too.
- **No stutter.** Sounds are loaded when a file opens (or when its sounds change), not on Play, and their memory is touched page by page then, so the audio thread never waits for the disk or a page fault. The contract suite fails an instrument that allocates, locks or waits during rendering. Playback starts within 100 ms (the milestone's gate).

## The engine, as built

Built in slice 2, second pull request (`oxiguitar-play`'s `schedule` and `engine`; interface 1.3's `realtime`). Where it differs from the plan above, this is what holds:

- **No feeder thread.** The plan had the audio thread read queues a thread fills ahead; refilling them would need waking that thread (a system call on the audio thread) or polling. Instead the timeline becomes a `Schedule` off the audio thread (every note in the plugins' form, sorted by start and by end, routed to its source, with the clicks), handed to the engine whole, and the audio thread reads it directly: a cursor into each list, a binary search on a seek. Lock-free single-producer queues (rtrb, MIT OR Apache-2.0) carry the window's commands in (play, pause, seek, loop, speed, the mixer, the metronome, a new schedule or new sources) and carry back what the engine lets go of (an old schedule, old sources), which the window drops, and the song's end. A new schedule or new sources are taken only while nothing plays (no editing while playing).
- **Time.** The engine keeps an anchor: a device frame, the score's time there, and the score's seconds per frame (the speed over the rate), reset only on play, seek, loop and speed changes. A frame's time is the anchor's plus the frames since times the step: nothing accumulates, so nothing drifts. An event at time `t` happens on the first frame whose time is at or after `t`. Each device callback is split at every event (and at the engine's largest piece); the events of a piece happen on its first frame, and a piece may have events and no frames.
- **Notes cross by value** (`RtNote`: id, track slot, key, velocity, string, sound, harmonic, attack, flags, start and end in score seconds), with their pitch curves as runs of one shared array of points that stays put while anything sounds. No pointer is held across calls.
- **Sources render all the time**, even stopped and during the count-in, so a note let go of fades out as its sound set says instead of being cut. Gains ramp over a piece when the mixer changes (no zipper noise), and the first piece takes them at once, so a note's first frame is never silent. Pan is constant-power.
- **Loops** jump on the frame of their end, with "all off" first; **the count-in** plays the timeline's count-in clicks before the start point, then the music; **the metronome** is a short sine (higher on the bar's first beat) the core synthesises, so it needs no sound set.
- **The clock.** After each callback the engine publishes, through a sequence lock the audio thread never waits on, the device frames handed over at the callback's start, when it started, the delay to the speaker plus the sources' largest latency, and its latest pieces of played time. `Control::heard` extrapolates from the callback's start to now (at most a second), takes the delay off, and maps the frame back to the score's time through those pieces, so a loop or a seek moves the cursor exactly when the sound moves. Lining up sources of different latencies comes with the first source that has any (ours have none).
- **Sample rate.** Streams ask for 48 kHz; where a device refuses, the engine runs at the device's rate (instruments are told the rate when prepared). Converting to 48 kHz for an effect that needs it (NAM) comes with slice 6.
- **Gates** (`oxiguitar-play/tests/engine.rs`, against a stand-in device with callbacks of 1 to 1024 frames): every note starts and ends on its frame at 25, 100 and 200 %, and the sound starts on the first note's frame; loops and seeks land on their frames; the count-in comes first; ten minutes of notes end on their frames and the clock maps every device frame to its time exactly; volume, pan, mute, solo and the metronome. `tests/engine_allocations.rs`: nothing is allocated while playing, with a loop, the count-in and the metronome. The contract suite plays the test plugin's sine through the engine and finds the first note's first frame where it belongs.
- **The contract suite's real-time checks**: each instrument and effect is prepared and played a short script; a note must start within the instrument's declared resolution and not before; the SDK's counting allocator (every `.oxp` built with `export_plugin!` has it) must count nothing while it renders; and on Linux the renders run in a forked copy of the test behind a seccomp filter that traps every system call. A test plugin that misbehaves on purpose shows each check failing.

## The audio devices, as built

Built in slice 2, third pull request: `plugins/audio-pipewire` (priority 20), `audio-alsa` (10), `audio-wasapi` and `audio-coreaudio`, each a few lines over `crates/oxiguitar-audio-cpal`, which they share, and each built only for the system its manifest names (`scripts/build-plugins.sh` reads the manifest's `os`).

- **The interface** (`oxiguitar_plugin_api::audio_device`): the service `audio-device` with the methods `open` (an `Open`: the stream's number from the host, the rate wanted, a device's name or the default; answered with an `Opened`: the rate, channels and buffer size it runs at, and the output's name), `close` and `devices`. From `open` on, the device's callback calls the host table's new `render` with the stream's number, its buffer and the delay to the speaker that cpal reports (`playback − callback` of the callback's timestamp), until `close` has returned. The host keeps each stream's target (the engine) in a lock-free slot the callback reads; closing takes it back off the audio thread.
- **The device's side**: streams live on a thread of their own that sleeps until asked to open or close one. The rate asked for when the device takes it, in f32 when it can (16- and 32-bit integers are converted through a buffer made when the stream opens); the system's default output, or the first that opens. A stream that breaks is said in the footer. The callback allocates nothing.
- **Choosing**: the host's usual service choice: settings.json's `services` pin, else the highest priority whose probe says it works (PipeWire's probe connects to the sound server; without one, ALSA plays). A plugin whose system library is missing is withdrawn quietly: "Can't run here: it needs libpipewire-0.3.so.0, which isn't installed on this system".
- **`oxiguitar-cli play FILE`** plays a score from the terminal: from a bar, looping bars, at 25 to 200 %, with the count-in and the metronome, only some tracks, on a named output; it prints each bar as it is heard, through `Control::heard`. Each track plays through the first installed instrument for its class.
- **Building** needs `libasound2-dev`, `libpipewire-0.3-dev` and `libclang-dev` on Linux (CI, the release jobs, `debian/control`, the README); the plugins' .deb depends on the libraries they link.

## The SoundFont plugin, as built

Slice 3, first pull request: `plugins/soundfont` (`oxiguitar.soundfont`), the instrument `soundfont`, which plays every class of track. In the basic plugins.

- **rustysynth 1.3.8, as published**, one synthesiser per track (two, in fact: see "Stopping"), dry (its reverb and chorus off, as in the listening tests: a track's effects come after it), blocks of 8 frames, 128 voices. Notes start at most 7 frames after their event, which the renderer declares as its resolution: 0.15 ms at 48 kHz, 0.16 ms at 44.1 kHz (rustysynth's smallest block is 8, so a device that refuses 48 kHz costs that hundredth of a millisecond). Its two known gaps, linear interpolation and the modulators it ignores, are accepted as they are (Mateus, 25 Oct 2026).
- **Channels**: a track with strings gives each string a channel of its own (0 up, past the drum channel 9), so a new note on a string ends the one before it, as on the instrument, and later a string's pitch can move alone; a track without strings plays on channel 0; a drum kit on channel 9, where rustysynth plays bank 128 and the program is the kit. Every channel takes the track's General MIDI program at bank 0; a program the set lacks falls back as rustysynth does (bank 0, then the set's first preset). A note's end is followed by its id: a note ended early by the next one on its string isn't ended twice, and of two notes of one key on one channel the first to end leaves the other sounding.
- **Stopping** (the engine's "all off": stop, seek, a loop's jump, a change of speed): what sounds fades out over 2.5 ms instead of being cut, which would click, while the notes on the same frame start at full level. Each track has a second synthesiser over the same set; the one that sounded fades out while the other takes over.
- **Sets**: the user's `soundfonts` folder (the manifest's `folders`) and the system's, read only (on Linux `/usr/share/sounds/sf2`, `/usr/share/sounds/sf3`, `/usr/share/soundfonts`; `gm.dls` on Windows; `gs_instruments.dls` on macOS), the folder and two levels of folders inside it, every link followed and each file counted once. A set's kind goes by its first bytes, not its name. A set is loaded once and kept while a track uses it.
- **Choosing** (second pull request): the settings window (Tools → Plugins…, SoundFont, Settings…) picks a set for guitars (the fretted class but basses), basses (General MIDI programs 32 to 39), drums and everything else, kept in the plugin's settings by path; "The best found" (the user's before the system's, the larger before the smaller) is the default and what a pick falls back to when its file has gone. A track whose set won't load takes the next that does.
- **SoundFont 3**: decoded with lewton on every core into an in-memory SoundFont 2 (`sf3.rs`; MuseScore's files leave odd chunks unpadded, which the reader allows for), then kept in the plugin's cache folder under a name made from the file's path, size and time, so it is decoded once: MuseScore General Lite took 6.6 s on the session's two cores the first time and 0.75 s after, for the whole render. `oxiguitar-cli` creates nothing in the user's folders (the host now names a plugin's own folders to it without creating them, `Plugins::use_folders_read_only`), so there it decodes each time.
- **DLS**: our reader (`dls.rs`) turns levels 1 and 2 into an in-memory SoundFont 2: each wave a sample (8-, 16- and 24-bit PCM, the first channel), each instrument a preset (the locale's MSB as the bank; drum kits at bank 128), each region a zone with its keys, velocities (level 1's empty ranges taken as every velocity), tuning, attenuation, loop and key group, and each connection block that SoundFont 2 has a generator for as that generator: both envelopes' times and levels, the LFOs, pan, attenuation, the filter, the LFO and modulation envelope to pitch and filter, key scaling of pitch and of envelope times. Blocks that would need a modulator (velocity to attack, controllers) are left out and counted; rustysynth would ignore them anyway. A test on the Windows and macOS runners converts the system's own set and plays A4 at 440 Hz.
- **Basic sets**: every set the system provides counts as basic, a set in the user's folder doesn't (Mateus, 25 Oct 2026). When a preparation uses only basic sets, the footer says so once, ever, as a warning with a link to the manual's "Better sounds" page (remembered in the plugin's settings as `warned_basic_sets`; `oxiguitar-cli`, which saves no settings, says it every time on the standard error). A set's own envelope plays as it is written: SoundFont 2's default delay and attack (−12000 timecents, about 1 ms each) mean most sets' notes sound about a millisecond after their frame, the same for every note, as in FluidSynth.
- **The effects in MIDI terms** (third pull request; PLAY-3), through rustysynth's public API only, controllers updated every 8 frames: bends, the whammy bar and slides as the notes' pitch curves, sent as pitch bend on the string's channel (range 24 semitones, 0.3 cents a step; deeper dives stop there); vibrato as a curve of our own on top (30 cents at 5.5 Hz, the whammy bar's 60 cents at 4.5 Hz, full depth after 0.1 s, in real time so the speed doesn't change it); notes not picked (hammer-ons, pull-offs, legato slides, trills) carry on the note sounding on their string, bent to their pitch, with no new attack (the string keeps ringing and decaying, as it does), or start softer (×0.7) where there is none; palm mutes end after 0.15 s at ×0.9 and dead notes after 30 ms at ×0.6, the set's own sound damped; harmonics at the timeline's key, natural, artificial and tapped ones on clean guitars (programs 24 to 28) through General MIDI's Guitar Harmonics (31); slapped and popped notes on basses (32 to 35) through Slap Bass 1 and 2 (36, 37); a swell rises from −60 dB over its note and a fade out falls over the note's second half (expression). A program a note switched to goes back with the next note. The SDK's `Piece::pitch` (new) gives the whole array of pitch points, so a renderer can follow a note's curve across calls.
- **The contract suite** puts its own test set (`oxiguitar-plugin-test`'s `TEST_SET`: a looped 480 Hz sine with no delay and no attack, a melodic preset and a drum kit) in the `soundfonts` folder of every plugin that lists the folder, so an instrument that plays from a set shows it keeps time. The plugin's own SoundFont 2 writer (`sf2.rs`) makes it, and a test checks the copy is current.
- **`oxiguitar-cli play FILE --wav OUT`** plays into a WAV file (48 kHz, 16-bit stereo) through the same engine, faster than real time and without a sound card, with two seconds after the end: for tests, listening packs and Mateus's ears. It isn't WAV export (PLAY-7, slice 7).
- **Packages**: the `oxiguitar-plugins-basic` .deb recommends `fluid-soundfont-gm | musescore-general-soundfont-small`, the .rpm `fluid-soundfont-gm`; `scripts/package/linux.sh` fails if either loses it.

## The window, as built

Slice 4, first pull request: the player in the window (`oxiguitar-app`'s `player.rs`, the controls' rules without window code; `sound.rs`, the player's thread; `playing.rs`, the window's side).

- **The player's thread** prepares the instruments when a file opens and whenever the tracks' sounds change (an instrument, a tuning, a capo, a plugin's track settings, a track added or removed), so Play never waits for a set to load or a SoundFont 3 to decode; after every change it builds the timeline and the schedule again, the newest of several changes only. It sleeps until asked. Choosing and preparing the instruments is shared with `oxiguitar-cli play` (`plugin_source::plan` and `prepare`): each track goes to the first installed instrument for its class, the tracks of one instrument share one instance, and an instrument that can't get ready leaves its tracks silent, said once in the footer. Two equal plans need no preparing again, so typing notes never reloads a set.
- **The output** opens on Play, not before (no device is held while nothing plays), stays open while paused, and closes 2.5 s after Stop or the song's end, once the last notes have rung out, unless Play came again meanwhile. Between streams the engine, with the instruments it holds, comes back to the player's thread: the stream's callback owns it, and dropping the callback (which the host does on the closing thread, never the audio thread) hands it back. A device that refuses 48 kHz gets an engine at its own rate, and the instruments are prepared again at it. While the output is closed the window sends the engine nothing (its queue would fill with no device to empty it); everything it has to know goes when the output opens.
- **The transport**: Play from the caret's beat; Play Selection from the selection's first beat, stopping on the frame of its last beat's end (the engine's new `Control::play_until`, gated like a loop's end); Loop over the selection, or the whole song; Pause leaves the caret on the beat heard, Stop puts it back where playing began, Rewind goes to the song's start or the loop's; count-in, metronome, speed 25 to 200 % in steps of 5. Space plays and pauses (Guitar Pro 8's key); Ctrl + Left and Right move a bar.
- **No editing while playing**: `OpenScore` holds whether the sound runs; the worker refuses every edit request (notes, tools, undo and redo, plugins' tools) and `apply` refuses plugins' changes while it does, from Play until Pause or Stop. The first refused edit of a session says so in the footer.
- **The frames**: while the sound runs, the window's `play-frame` is bound to Slint's `animation-tick()`, so the window draws a frame whenever the screen can show one, and each frame asks the player (`playing::frame`) for what it shows, from `Control::heard`. Nothing is computed on a timer, and when nothing plays no frame is asked for. Each frame also drops what the engine handed back and notices the song's end. The track overview's playhead follows the sound.
- **The mixer**: each Tracks row's volume, pan, mute and solo go to the engine as they move; the master level is a square-law control whose top is +12 dB and whose default, about +6 dB (`engine::MASTER_USUAL`, also `oxiguitar-cli play`'s), was measured: over the 104 corpus songs through FluidR3 at unity gain, peaks sit at a median of −9.4 dBFS (a tenth of them below −14.6, a tenth above −5.8, one at 0) and the loudest second at a median of −23 dBFS RMS; one guitar alone at mf peaks near −27. So the engine now ends with a **limiter**: no frame leaves louder than −1 dBFS; a frame that would is brought down to it at once and the gain comes back over 80 ms. It looks at no frame ahead, so it adds no latency and the clock stays exact; below −1 dBFS it changes nothing. With the default level, two corpus songs out of 104 have peaks held down by more than 3 dB.
- **The cursor** (second pull request; `cursor.rs` without window code): a 2 px line in the player's blue (the caret is green) moving with the sound across the system's staves, and the beat being heard lightly boxed in the same blue (Mateus, 26 Oct 2026). The line goes from one beat's column to the next in proportion to the time between them, so it moves as the music does even where the engraver spaces beats unevenly; after a bar's last beat it goes on to the bar line. Both are drawn over the tiles in canvas points, like the caret, so a frame redraws no tile. Paused, they stay where the sound stopped, with the caret; moving the caret from there ends the pause (Play starts from the caret). **The page turns** to keep the cursor in sight: when its line nears the view's edge or its system leaves the view, the line goes near the left and its system near the top, so the music ahead shows; between turns the view stays still, for reading. **The track overview's playhead** follows the sound, stays where it paused, and when stopped shows the caret's place; a click on an overview moves the sound there while it plays, the caret otherwise. **The visual metronome** (a button beside the metronome's) lights on each click of the timeline's metronome, bright on the bar's first beat and dimmer on the others, fading over 0.12 s of the music, whether or not the clicks are heard.
- **Greyed out** while nothing can play the open score: no instrument plugin, no sound set, no audio output (no audio-device plugin works here). The tooltips add the reason, and the footer says what to get, with the Better sounds link when it is a sound set.

## SFZ, as built

Slice 5 (in v1.0, Mateus, 26 Oct 2026): our own sampler in the SoundFont plugin. Mateus's answers (26 Oct 2026):

- **An SFZ instrument plays only where the user picks it** in the settings window. One `.sfz` file is one instrument, not a General MIDI set, so it is never "the best found": the General MIDI sets stay the default for every role until a pick.
- **Guitars split in two**: Electric guitars (General MIDI 26 to 31) and Acoustic guitars (24 and 25) each get a pick, since an SFZ guitar is one or the other.
- **Samples whole in memory**, each at its own bit depth (16-bit as 16, 24-bit as 24), loaded before Play: glitch-free and full quality. A band with the big kits can take several gigabytes (SM Drums about 2.2 GB, Naked Drums about 2.5 GB decoded); streaming from disk could come later if testers' machines struggle.

What the recommended sets use, surveyed on 26 Oct 2026 (Karoryfer's guitars, basses and kits, SM Drums, Naked Drums, DrumGizmo's Muldjord and DRS kits: 808 instruments, about 254,000 regions): `#define` and `#include`, `<curve>`s, controllers that set levels, pans, envelopes, LFO depths and crossfades from the instrument's own `set_cc` values (often above 127: ARIA's), round robins (`seq_length`, `seq_position`), random layers (`lorand`, `hirand`), velocity layers and curves, release samples with `rt_decay`, key switches (`sw_lokey`, `sw_hikey`, `sw_last`, `sw_default`), choke groups (`group`, `off_by`, `off_mode`), loops, LFO vibrato, bends. A few use second filters, EQ bands, ARIA's flexible envelopes and variables; those wait. Since OxiGuitar moves no controller while playing, a controller keeps the value the instrument gives it, or one our mapping chooses for an articulation.

First pull request, reading (`plugins/soundfont/src/sfz/`):

- **`text.rs`** reads a file into headers and opcodes as sfizz and ARIA do: a value runs to the end of its line but stops before another `name=`, a header or a directive, so `sample=Hit 1.wav lokey=36` keeps the space in the name; `#define $NAME value` takes one word (more may follow on the line); a `$` takes the shortest defined name; `#include` is relative to the top file's folder, may repeat, and nests at most 32 deep.
- **`region.rs`** holds every opcode those sets use as typed values, with sfizz's defaults, and keeps controller opcodes as written (`amplitude_oncc7=…`, `ampeg_attackcc1=…`, `lfo02_pitch_oncc113=…`, `locc64`, `xfin_locc1`), worked out when a note starts. Note names (`c4` is 60). Regions started by a controller (`on_loccN`) never play.
- **`instrument.rs`**: `<global>`, `<master>`, `<group>` and `<region>`, each resetting what is below it; `<control>`'s `default_path`, `set_ccN` (and `set_hdccN`), `note_offset` and `octave_offset`; `<curve>`s and the seven built-in curves; controllers 7, 10 and 11 start at 100, 64 and 127 and move the level and pan unless the instrument uses them itself (as in sfizz). What it doesn't know is counted by shape, and problems kept, so a set that plays badly can say why. `OXIGUITAR_SFZ_DIR=… cargo test -p oxiguitar-soundfont-plugin survey -- --ignored --nocapture` reads every instrument under a folder and prints both.
- **`sample.rs`**: WAV (our own reading, so the data is copied as it is and the `smpl` chunk gives the loop and unity note; a `data` chunk longer than the file is taken to its end), FLAC (claxon) and Ogg Vorbis (lewton, as floats). More than two channels keep the first two.
- **`mod.rs`**: an instrument and all its samples load before anything plays, the samples in parallel on every core; samples are shared by every instrument that plays them and let go when none does.
- **Finding**: `.sfz` files in the `soundfonts` folders, five levels deep (Naked Drums keeps its instruments in `Wilkinson Audio/Naked Drums/Stereo/`), leaving out the files other `.sfz` files include (Karoryfer's `modules/`).

Second pull request, the sampler (`sfz/sampler.rs`, `sfz/sinc.rs`), with sfizz's behaviour as the reference:

- **Tracks**: the renderer (`play.rs`) holds, for each track, rustysynth's synthesisers or an SFZ sampler (`Sound::Font`, `Sound::Sfz`), side by side in one instrument instance; `prepare` loads a track's pick, SFZ or not, and anything that fails to load falls back to the General MIDI sets, with a warning in the footer ("…; playing a General MIDI set instead"), as do samples an instrument can't find. The SFZ instruments and their samples stay loaded while a track uses them. Until the settings window lists them (the next pull request), `settings.json` picks them by path.
- **Sample-exact**: the engine already splits each callback at its events, so a note's voices start on its frame (no blocks, unlike rustysynth's 8).
- **Which regions play** a note: key and velocity ranges; the last key switch pressed (`sw_lokey`..`sw_hikey`, `sw_last`, `sw_default`; `sw_down`, `sw_up`, `sw_previous`); controllers in their ranges; one random number per note against `lorand`..`hirand`; each region's own round-robin count, counted on every note in its keys and velocities as sfizz counts it; triggers (`attack`, `first`, `legato`; `release` and `release_key` on the note's end, softer by `rt_decay` for each second held). Regions of a group choke the voices whose `off_by` names it (`off_mode` fast: 6 ms, `time`: `off_time`, `normal`: their release); `polyphony` and `note_polyphony` stop the oldest. Each track has 256 voices; past that the oldest released voice is taken.
- **Reading a sample**: a 32-tap Kaiser-windowed sinc, a table of 1024 positions for each range of speeds, so a 44.1 kHz sample stays flat to about 18.5 kHz at 48 kHz, and pitched up it is cut at the new Nyquist frequency instead of aliasing. 16-bit, 24-bit and float samples are read as they are kept.
- **Pitch**: the key's distance from the region's centre (`pitch_keycenter`, or the sample's own unity note) times `pitch_keytrack`, `transpose`, `tune`, `pitch_random`, `pitch_veltrack`, controllers; the timeline's pitch curve (bends, the whammy bar, slides) in cents with no range limit, and the same vibrato as the SoundFont path; pitch envelope and LFOs.
- **Level**: `volume` (and ARIA's group, master and global volumes) and `amp_random` in decibels; `amplitude` and its controllers multiplied; velocity through `amp_velcurve_N` points or the square curve, with `amp_veltrack`; key and velocity crossfades and controller crossfades (`xfin_*`, `xfout_*`, power or gain curves); `amp_keytrack`. Controllers 7, 10 and 11 start at 100, 63.5 (exactly the middle, as in sfizz) and 127.
- **Envelopes**: sfizz's: a linear attack from `start`, hold, an exponential decay and release (78 dB over their time), then 50 ms to silence; a sustain under 0.32 % releases by itself (drums); velocity and controllers move each stage.
- **Filters** (`fil_type` with `cutoff`): one-pole and RBJ biquads (two, four and six poles as cascades), cutoff moved by key, velocity, randomness, controllers, the filter envelope and LFOs, `resonance` in decibels. **LFOs**: SFZ 2's numbered ones (waves, delay, fade, phase; pitch, volume, amplitude, pan, cutoff) and SFZ 1's three.
- **Pan, width and position**: sfizz's law (equal power, the middle unchanged); a mono voice is panned once, a stereo one panned, mixed by its width and panned again by its position.
- **Loops**: the region's loop, else the sample's own; `loop_continuous` until the release ends, `loop_sustain` while held, `one_shot` to the end whatever the note does; `offset`, `offset_random`, `end`, `delay`.
- **Strings**: a new note on a string ends the one sounding on it, its release samples playing.
- **Stopping** (stop, seek, a loop's jump): every voice fades out over 2.5 ms; the next notes start at full level.
- **The real-time rules**: voices, held notes and each key's list of regions are made in `Sampler::new`; the sinc tables once, before anything plays. The contract suite's real-time checks run on the SoundFont plugin with an SFZ instrument picked (`crates/oxiguitar-plugin-test/tests/ours.rs`): notes on time, nothing allocated, no system call while rendering.

Third pull request, picking SFZ instruments and the score's effects through them:

Settings keys `electric-guitars`, `acoustic-guitars`, `basses`, `drums`, `other`; 0.9's `guitars` pick holds for both guitar rows until one is changed, when it is copied to the other.

A `.sfz` file is listed only when it plays on its own: it has regions, uses no `$name` it never defines and has no opcode before its first header (Karoryfer's sets keep parts that work only when included); the check is kept while the file is unchanged.
- **What the score asks** of a note on an SFZ track: a drum's key (General MIDI's) moved to the kit's, an articulation from the set's map, or, where the map has none, the SoundFont path's treatment: palm mutes end after 0.15 s, dead notes after 30 ms; either way palm mutes play at ×0.9 and dead notes at ×0.6 of their velocity (a set's own staccato is often its loudest sample: Black and Green's peak near 0 dBFS, its ordinary mf notes near −15); notes not picked (hammer-ons, pull-offs, legato slides, trills) play the set's **recorded hammer-ons** where its map has them (Black and Green; Mateus compared both by ear and found them more natural, 26 Oct 2026), and otherwise **carry on the ringing string**, its voices bent to the new pitch with no new attack, or start at ×0.7 where nothing rings. ## Sounds

- **Sound sets are files in a folder, like plugins.** A `soundfonts` folder sits beside `plugins` in the user's folder: `~/.local/share/oxiguitar/soundfonts/` on Linux, `%APPDATA%\OxiGuitar\soundfonts\` on Windows, `~/Library/Application Support/OxiGuitar/soundfonts/` on macOS, `soundfonts/` in `OXIGUITAR_HOME`. OxiGuitar creates it at start, as it does `plugins`. Put an `.sf2`, `.sf3` or `.dls` file in it, or an SFZ instrument's folder (its `.sfz` files with their samples); nothing else is needed.
- **The system's own sets are read too**, never written: on Linux `/usr/share/sounds/sf2`, `/usr/share/sounds/sf3` and `/usr/share/soundfonts` (FluidR3, MuseScore General, TimGM6mb and others from the distribution's packages); on Windows `C:\Windows\System32\drivers\gm.dls`, the General MIDI set every Windows has; on macOS the General MIDI set in CoreAudio (`gs_instruments.dls`). So it plays out of the box everywhere. The `oxiguitar-plugins-basic` .deb and .rpm **recommend** a General MIDI sound set package (`fluid-soundfont-gm` or `musescore-general-soundfont-small` on Debian and Ubuntu; `fluid-soundfont-gm` on Fedora), which the package manager installs unless told not to.
- **Choosing.** The sound plugin's settings window (opened from the plugin manager: Tools → Plugins…, the plugin's Settings…) lists every set found, with its folder, and picks one for guitars, one for basses, one for drums and one for everything else. The choice is global, for every file (Mateus, 21 Oct 2026). Until the user picks, the best set found is used: a set in the user's folder before the system's, the larger before the smaller.
- **The way to better sound is in sight once.** Every set the system provides counts as basic; a set in the user's `soundfonts` folder doesn't (Mateus, 25 Oct 2026). The first time playback uses only basic sets, the footer says, as a warning, that better sounds can be installed, and never again (the plugin remembers it in its settings: nothing is warned about permanently), with a link to the manual's "Better sounds" page, which says what to get, where from, its licence and size, and where to put it, by instrument (guitars, basses, drums), with the DI guitar set for NAM.
- **What we recommend** (kept in `claude/sound-research.md` and the manual; all free to use; none bundled): MuseScore General and FluidR3 (MIT) for everything; FreePats' guitars (CC0, with a raw DI bank), Karoryfer's Black and Green Guitars and Shinyguitar (CC0); Karoryfer's basses (CC0); SM Drums (public domain), Naked Drums (CC BY 4.0), Karoryfer's drums (CC0). Before the manual names them, Mateus listens to renders of the reference songs with each.

## Libraries

| Job | Choice | Why |
| --- | --- | --- |
| SF2 synthesis | **rustysynth** 1.3.8 (MIT, no dependencies; decided by Mateus, 25 Oct 2026): the better supported (14 commits in 2026, releases 1 and 20 Oct 2026, outside pull requests merged within days). Its gaps against OxiSynth and FluidSynth: linear sample interpolation (the top octave −2.5 dB, some aliasing: by ear "a tad less natural") and no custom modulators (every General MIDI set defines them: FluidR3 746, MuseScore General 2486). **rustysynth is used exactly as published: no fork, no `[patch]`, no edited copy, and no plan that waits on a change upstream** (Mateus, 25 Oct 2026, withdrawing the fork the plan first proposed). **Its gaps are accepted as they are** (Mateus, 25 Oct 2026: the difference is marginal and not worth the work): no resampling at load, no baking of modulators, no correcting filter on its output. The plugin drives it only through its public API, handing it SF3 and DLS sets as in-memory SF2s. OxiSynth (LGPL-2.1, FluidSynth's design, dormant) stays in the spikes as a reference only. |
| SF3 | rustysynth, after decoding the Ogg Vorbis samples into an in-memory SF2 (lewton, MIT OR Apache-2.0) | Measured: MuseScore General Lite (40 MB) becomes a 216 MB SF2 in 6 s on one slow core, done when the set is first loaded, in parallel on real machines, and plays like FluidSynth's render of the .sf3. |
| DLS (Windows, macOS) | Our reader, turning DLS into an in-memory SF2 for rustysynth (DLS articulations map to SF2 generators; FluidSynth 2.5's DLS loader, LGPL, is the reference) | So both play out of the box. Checked on GitHub's Windows and macOS runners, which have the sets. |
| SFZ | **Our own sampler** | No Rust SFZ engine fits: xsynth (LGPL-3.0) leaves out modulation envelopes and LFOs, sofiza is a parser from 2022. The best free guitars, basses and drums are SFZ: round robins, velocity layers, release samples, key switches, choke groups. WAV (our own reading, which copies the data at its own depth and reads the loop; hound reads neither), FLAC (claxon, Apache-2.0) and Ogg (lewton) samples. Sample-exact starts. sfizz (BSD-2-Clause) is the reference for behaviour; no code is taken from it. |
| Audio devices | **cpal** 0.18 (Apache-2.0; Debian packages cpal, lewton and hound) | Every system's API, PipeWire included; reports when each buffer will be heard. Measured: rendering three tracks inside its callback, no allocation. |
| NAM (M7) | Decided in M7 after the speed test on every system (the brief's rule); see "NAM" below | |

All of them speak plain `f32` sample buffers, planar or interleaved: the synthesiser fills a track's left and right buffers, NAM processes a mono buffer in place, cpal takes interleaved frames. They fit without conversion beyond copying, and the spike runs the whole chain in 64-sample callbacks with no allocation.

## NAM (for M7)

Two pure-Rust engines exist, both run NAM's `.nam` files, both allocation-free on the audio thread (measured for nam-rs):

- **nam-rs** 0.4.0 (MIT; serde, serde_json, thiserror): WaveNet A1 and A2, LSTM, slimmable models; plain Rust, so it builds for every target we ship. NAM's standard WaveNet at 2.6–4.9× real time on one core of GitHub's runners (Linux and Windows on x86_64 and ARM64, an M1), median 240–520 µs per 64 samples.
- **NeuralAmpModeler-rs** 1.0.1 (Apache-2.0): hand-written AVX2 and AVX-512 kernels, cabinet IR convolution, resampling, oversampling, a noise gate. **About ten times faster**: the standard WaveNet at 25× real time (median 52 µs per 64 samples on an AMD EPYC 7763), the same model's output as nam-rs within 6e-6 (both match NAM's reference). But it builds only for **Linux on x86_64** with the x86-64-v3 baseline (AVX2, FMA: Intel from 2013, AMD from 2015): besides refusing other processors, its memory code is Linux's and glibc's throughout (`memfd_create`, huge pages, mirrored ring buffers, `__errno_location`, pinned glibc symbols), so it doesn't build for Windows (seen on GitHub's runner) or for macOS. It needs Rust 1.99 (we moved to it, 24 Oct 2026). Several releases this month were yanked.

**Decided (Mateus, 25 Oct 2026): NeuralAmpModeler-rs on Linux x86_64, nam-rs everywhere else**, and the NAM plugin ships in v1.0 (the spike showed the approach works). The sound is the same everywhere, since both match NAM's reference and each other to under 1e-5; only the cost per track differs. If NeuralAmpModeler-rs gains Windows or macOS later, those builds switch too. The plugin's manifest needs a condition on the processor's features, so that an x86_64 machine without AVX2 gets the nam-rs build instead of crashing: interface 1.3's `cpu` condition (added before 1.3 froze, Mateus, 26 Oct 2026): the NeuralAmpModeler-rs build lists `avx2` and `fma`, the nam-rs build lists none, both carry the same id and version, and the host uses the one needing more features where both can run. The guitar signal for NAM: a DI sound set (FreePats' Direct bank, CC0) through the SoundFont plugin; the brief's plucked-string model stays for M7.

Per-track NAM settings (whether to use NAM, which model and impulse response, input and output level) belong in the track dialog, added by the NAM plugin only when it is installed (Mateus, 21 Oct 2026): interface 1.3 gives plugins sections of the track dialog. Cabinet IRs we could ship: Guitarix's BestPlugins pack (GPL-2.0-or-later). Amp captures: users bring their own, as the brief says; ones we'd ship need a licence that allows it.

## The plugin interface (1.3)

Additions only, at the ends of enums, as every minor version (frozen with the release that brings them):

- **Instruments.** The manifest's `instruments` key (in 1.0) comes alive; the SDK's `Instrument` trait: `prepare` (off the audio thread: the tracks it plays, the sample rate, the largest callback; load what they need), `render` (on the audio thread: this callback's events per track, into a buffer per track), `latency`. Instruments declared by a plugin built for an interface before 1.3 are ignored (Mateus, 19 Oct 2026).
- **Audio devices**, as services (`audio-device`): open a stream at a rate and callback size, call the host's render function from the device's callback with the delay to the speaker, report errors and device changes. The host picks the first available by priority, or the one settings.json pins.
- **A settings window per plugin**, opened from the plugin manager's Settings… for plugins whose manifest asks for one, built from the same widgets as a plugin's tab (1.1), its values kept in the plugin's own part of settings.json.
- **Footer messages with a link**, opened in the system's browser when clicked.
- **Effects**: a plugin can process a track's buffer after its instrument (manifest `effects`, SDK trait `Effect`: `prepare` off the audio thread, `process` on it, `latency`), per track, in the order the track lists them; the NAM plugin is the first.
- **Sections of the track dialog**: a plugin adds its own rows to the track dialog (the widgets of a tab, 1.1), kept per track in the score's settings for that plugin; without the plugin they don't show. Saved beside the score in `FILE.oxg` (`song.gp3.oxg`; Mateus, 25 Oct 2026), since no score format holds them; built (plugins.md, "Interface 1.3").
- **The plugin's own folders**: its data folder (brief: "The plugin's own data folder", in the wishlist) and the sound-set folders, handed over by the host.
- The contract suite checks every instrument for allocations, locks and waits while rendering, and that it keeps time (a note asked for at a sample starts there, within the instrument's declared resolution).

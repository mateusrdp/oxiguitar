# Interface design rules

These rules come from Mateus's review of the GUI spike (16 October 2026) and his plan for a plugin-first window (18 October 2026). They apply to `oxiguitar-app`, and to any plugin that adds tabs, toolbar sections or palette entries. The app (`crates/oxiguitar-app`, binary `oxiguitar`) follows them; the Slint spike in `spikes/gui/slint` stays as the reference for the palette, whose icons show greyed out from M2 and work with the editor in M3.

## The window

Five areas, a toolbar above them and a footer below (Mateus, 18 Oct 2026; docs/design/plugins.md, "The window"). The window's shape lives in `shell.rs` and the footer's messages in `footer.rs`, without window code, and both are unit-tested. The core's tabs and toolbar sections are entries in the same lists plugins will add to, so the window assumes no fixed set.

- **Menus:** File (Open… Ctrl + O, Export PDF…, Paper Size: A4 or Letter, Quit Ctrl + Q), View (Layout, Dark Interface, Dark Page, Dynamics, Toolbar, Panels: Top, Bottom F8, Left F7, Right), Tools (the tools, then Plugins…), Help (Keyboard and Mouse F1, About, which also lists the plugin folders in search order and says when safe mode is on).
- **Plugin manager** (Tools → Plugins…; `manager.rs`, `ui/plugin_manager.slint`): a separate, non-modal window, opened only from that menu entry and shown again (in front) when chosen again; Close hides it. One row per plugin file: a tickbox (only for files that can be enabled or disabled), the name and version, a sentence for its state (loaded, not loaded yet, disabled, not used because another file holds the same plugin, or why it can't be used), and the folder and file name, dimmed. A tick writes `disabled` in settings.json at once. Plugins can't be unloaded while the app runs (ADR 0008), so the row says what a restart changes ("Loaded: it stays in use until OxiGuitar restarts, and is disabled from then on"), one line beside Close says "Restart OxiGuitar to apply these changes" while any change waits, and unticking a loaded plugin also says so in the footer (Mateus, 18 Oct 2026). It follows Dark Interface. Nothing marks a plugin as ours or anyone else's (Mateus, 18 Oct 2026). When settings.json couldn't be read at start, the tickboxes are greyed out and one amber line says why. `oxiguitar --safe-mode` starts with no plugin used; the manager then says so and still lists every file. There is no Edit menu yet: in a viewer all its entries would be greyed out, so it comes with the editor in M3.
- **Toolbar** under the menus, in sections separated by a thin rule: File (Open, Save, Export PDF) and Edit (Undo, Redo). Only what users click often belongs there; settings made once, such as Dark Page, live in the View menu only (Mateus, 18 Oct 2026). Save, Undo and Redo are greyed out until the editor. Icons are our own SVGs in `assets/icons/ui/`, white strokes tinted by the theme, 18 px in 30 × 28 buttons; tooltips give the name and shortcut. View → Toolbar hides it. Plugins add sections with their own icons.
- **Four tabbed areas.** Top (the Player tab) and bottom (Tracks) span the window; left (Palette) and right (Inspector) sit beside the page. There is no Mixer tab: the mixer's controls sit in each track's row ("Track list", below; Mateus, 19 Oct 2026). Each has a tab strip: clicking a tab opens it, clicking the open tab's name or the strip's chevron collapses the area to its strip (a side area to a 26 px strip that opens again with a click), and View → Panels hides it altogether. Splitters resize them. Top and bottom start open, and so does the left once it holds the palette (greyed out until the editor, "Palette" below); the right starts collapsed while it holds only a placeholder. A tab whose content doesn't exist yet shows one muted sentence saying what it will hold.
- **Plugin tabs** (slice 3; `plugin_tabs.rs`, `ui/plugin_tab.slint`): a plugin's tabs join the area its manifest names, after the core's, titled from the manifest, so nothing is loaded until one is opened. Their contents are rows of the window's own widgets (labels, buttons, tickboxes, sliders, one-line fields, drop-downs, lists), in the window's style and colours, and canvases the plugin draws, as large as the room allows with their proportions, on the panel's own colour and redrawn when Dark Interface changes. A thread of their own asks the plugins and draws the canvases, so the window never waits for a plugin; drags it hasn't answered yet are merged. Rows that keep their shape are changed in place, so a canvas being dragged on is never rebuilt. While the plugin is first asked the tab says so, and contents it can't show become one muted sentence saying why (also in the footer, once).
- **Player** (top area): rewind, play, play selection, pause, stop; count-in, loop, metronome; and the Output drop-down that picks the output plugin. All are greyed out while no output plugin is installed, and the footer says where to get one.
- **Canvas:** the score, centred on `#242528` whether or not Dark Page is on (Mateus, 18 Oct 2026), with scroll bars. The **mouse wheel over the page scrolls it**, along the line in the Horizontal layout when it fits the window's height; **Shift + wheel zooms the score** around the pointer, about 9 % a notch (2^(1/8)) (Mateus, 18 Oct 2026, swapping the two; a Shift + wheel that the system turns into a sideways scroll, as macOS does, zooms too). Elsewhere in the window the wheel scrolls lists as usual. Arrow keys, Page Up / Page Down, Space, Home and End scroll too. Before a file is open, one muted line says how to open one. The wheel is handled in the window's raw events (`install_window_events`), where the pointer's position decides whether it is over the page, so no widget scrolls the page by accident.
- **Score zoom slider** bottom right, as below. The slider keeps the middle of the view in place. In the Vertical layout the lines are as wide as the window, so zooming, resizing or opening a side area reflows the bars.
- **Footer**, one line under everything: the latest message with a coloured dot (grey info, amber warning, red error) and, when there are several, how many. A click expands it to 160 px with every message of the session, newest first, scrollable; the chevron in its corner folds it back. It replaces M1's status pill. Messages stay until a newer one arrives. At start it says what the plugin folders lack (no output plugin, no read/write plugins), and nothing when everything is there.
- **Track list**, the bottom area's Tracks tab: number, the name, the instrument (strings or drums), and two **notation buttons**: a G clef for standard notation and the vertical TAB sign for tablature (tracks without strings have only the clef). The buttons are drawn by our renderer, centred on their ink and highlighted when on, like the spike's palette buttons (`icons.rs`). Any combination is allowed: standard notation, tablature, both, or neither, which hides the track; a notation button on a hidden track shows it in that notation (Mateus, 16 Oct 2026). There is no separate show tick: the buttons already show and hide tracks, and one control can't fall out of step with another (Mateus, 17 Oct 2026). The last shown track cannot be hidden. Tablature starts on only for fretted instruments (see engraving.md, "Clefs, tablature and keyboards"). Clicking a name shows that track alone; clicking another track's notation button adds it, so several tracks line up in one score without a separate "show all" switch — the buttons already do that job, so there's nothing left for a Multitrack menu item to add, and one less control to keep in sync (Mateus, 17 Oct 2026). Opening a score shows the Tracks tab; the area's height fits up to five tracks and the splitter changes it. The rules live in `tracks.rs`, without window code, and are unit-tested.
- **The mixer is in the Tracks tab** (Mateus, 19 Oct 2026): no tab of its own. Each track's row carries its mixer controls beside the notation buttons, all compact: a slider for volume, a knob for pan, and icon toggles for mute and solo drawn and highlighted like the notation buttons. The playback speed sits with the player's controls in the top area. Like those controls, the mixer's are greyed out until an output plugin is installed, and they work from M4 (PLAY-6).
- **Ticks in menus** are two-way bound in Slint and set from one place (`pick-layout`, `pick-paper`): a checkable item flips its own tick when clicked, which breaks a one-way binding such as `checked: layout == 0`, so the layout and paper items behave like radio buttons only this way.
- **Window title** is just "OxiGuitar" (no file name), as Mateus asked.
- **Icon:** the placeholder pick (`assets/icon/`, PNGs in `assets/icon/png/`) is the window icon on X11, Windows and macOS. Wayland compositors ignore window icons: they show the icon of the desktop entry named by the window's app id, `io.github.mateusrdp.OxiGuitar` (`assets/linux/`). The packages will install the entry and icons; for a build from source, `scripts/install-desktop-entry.sh` installs them for the current user.
- **Open and Export dialogs** are the system's own, through the XDG desktop portal on Linux; they run on their own thread so the window keeps drawing (on macOS on the main thread, as the system requires). If the session has no D-Bus for the portal, the footer says so and suggests `oxiguitar FILE`. A file named on the command line opens at start, which is also how file managers open files (UI-4). A file dropped on the window opens too; of several files, the first opens. This works on Windows, macOS and X11 (winit's `DroppedFile`), **not on Wayland**: winit 0.30 and Slint 1.18 report no drops there, and a workaround of our own (`unsafe` plus polling) was rejected. ADR 0006 says what has to change upstream. On macOS a double-click in Finder starts OxiGuitar but doesn't open the file: macOS sends it as an Apple Event that winit and Slint don't pass on, and catching it ourselves would need `unsafe` Objective-C glue (ADR 0007).
- **PDF export** writes the tracks shown, in the Page layout, on the paper chosen under File → Paper Size, always on a light page (EXP-1), next to the score by default.
- **Drawing:** a worker thread reads, engraves and draws 512-pixel tiles at the screen's pixel density; the window shows them as they arrive, nearest the middle of the view first, and keeps those near the view. Scrolling never waits for engraving. After a zoom, a new engraving or Dark Page, the old tiles (scaled to the new zoom) stay underneath until the new ones cover the view, so the canvas never goes blank.

## Principles

1. **Minimal.** Screen space belongs to the score. Every visible control must earn its place; when in doubt, leave it out, put it in a menu, or make it a shortcut.
2. **No labels that state the obvious.** No app name inside the window (the title bar says "OxiGuitar"), no caption repeating what a highlight already shows, no "Tracks" heading over the track list.
3. **Menus and one toolbar on top.** File, Edit, View, Help (and later Track, Note, Tools, Playback, as Guitar Pro has), then a single toolbar of sections (Mateus, 18 Oct 2026, replacing the M1 rule of menus only). Everything else lives in the four areas, which the user can collapse or hide. Display options live under View or in Preferences.
4. **The user decides what is shown.** Every area collapses and hides from View → Panels, the toolbar from View → Toolbar, and two have keys (F7 left, F8 bottom). Palette tools come in groups that collapse and expand with a click on their heading.
5. **Look like Guitar Pro 8, without copying it** (UI-1, UI-3): same places for things, same shortcuts, our own drawing.

## Zoom

There are two zooms, and they never share a control.

| Zoom | What it scales | How | Visible control |
| --- | --- | --- | --- |
| Interface | Everything in the window: menus, palette, panels, text | Ctrl + mouse wheel anywhere; Ctrl + `+` (or `=`) in, Ctrl + `-` (or `_`) out, Ctrl + `0` back to 100 %; numeric keypad too | None. Documented in Help → Keyboard and Mouse and in the manual. |
| Score | The score canvas only, 25 % to 400 % | Shift + mouse wheel over the page, around the pointer (Mateus, 18 Oct 2026); a slider in the bottom-right corner of the canvas | The slider: logarithmic, so 100 % sits in the middle; it snaps to 100 % near the middle; clicking its percentage returns to 100 %. About 170 px wide in all. |

Interface zoom follows browser steps (50, 67, 75, 80, 90, 100, 110, 125, 150, 175, 200 %) and multiplies the system's scale factor, so it stays right when the window moves to another monitor. It is caught before any widget sees it, so Ctrl + wheel over the score never scrolls it.

## View options

Everything about how the score is shown lives in the View menu:

- **Layout** (VIEW-3, M1): how staves are laid out, as in Guitar Pro.
  - **Page**: systems fill the page width, stack vertically and break into pages.
  - **Vertical**: systems fill the window width and stack vertically, with no pages.
  - **Horizontal**: one single long line, scrolling sideways.
  - **Parchment**: one single long vertical column, with no page breaks.

  These follow Mateus's description (16 October 2026), checked against the Guitar Pro 8 user guide before they were built: they are GP8's Page – Vertical, Screen – Vertical, Screen – Horizontal and Page – Scroll ([engraving.md](engraving.md#layouts-view-3)).
- **Dark Interface**: the window's own colours, dark by default (Mateus, 18 Oct 2026), switched through Slint's `Palette.color-scheme`.
- **Dark Page** (VIEW-8): light notation on a dark page. Page colours are themes of the display list (`Theme::LIGHT`, `Theme::DARK` in `oxiguitar-display`), so the PDF can use them too. Off by default: the page is white.
- The View menu's choices (interface, page, dynamics, layout, paper) are kept in settings.json under `view` (`prefs.rs`) and restored at start.
- The toolbar, and the four panels under View → Panels.
- **Dynamics**: shows or hides dynamics markings (on by default), for scores where they clutter the page.

## Tools menu

The Tools menu lists the tools of `oxiguitar-tools` in order ([tools.md](tools.md)). An entry that cannot run on the open score is greyed out. Slint's menus have no tooltips, so the reason follows the name in brackets, such as "Infer Key Signatures (the score already has key signatures)"; descriptions go in the manual. Picking one applies it and shows its report in the footer. The file on disk is never changed: reopening it shows what it says. In M3 (the editor) applying a tool becomes one undoable command. Plugins add their tools to the same menu from M2.

The first tool is **Infer Key Signatures** (16 Oct 2026).

## Palette

- **Greyed out until the editor** (Mateus, 19 Oct 2026): the left area shows the editor's palette from M2, every tool as its icon in its group, disabled, so people trying OxiGuitar see where it is going. Each tooltip gives the tool's name and says it comes with the editor. The tools work from M3; the set and the groups follow Guitar Pro 8's palette, checked against its user guide.
- **Tuplets** (EDIT-10, M3): a palette tool with a shortcut makes triplets; "Other…" opens a small dialog to choose any grouping, n notes in the time of m, with the usual m filled in (Mateus, 16 Oct 2026). Shortcuts follow Guitar Pro's, checked against the GP8 user guide when the palette is built.
- Tools are grouped (Note values, Effects, and many more later). Each group has a small heading with a chevron; clicking it collapses or expands the group, and the state is kept while searching.
- A compact search field at the top of the palette filters tools by name (Ctrl + K focuses it).
- Buttons are 32 × 32 logical pixels, wrapping to the panel's width.
- **Icons are drawn by our renderer, not typed as text.** Each symbol is measured by its ink, scaled, and centred so the centre of its ink's bounding box is the centre of the button, with a margin all round. Note values share one scale so their sizes compare; other symbols are fitted one by one; text labels (H, P.M.) share one size. Icons are white on transparent and tinted by the toolkit, and redrawn for the screen's pixel density and the interface zoom.
- Every button has a tooltip with its name and shortcut. Selection is shown by the button's highlight only.

## Accessibility

Keyboard use is required: every tool has a shortcut (UI-2) and Tab moves through controls. Screen-reader support is a late nice-to-have, not a goal for v1.0 (decided 16 October 2026); Slint's AccessKit support keeps the door open.

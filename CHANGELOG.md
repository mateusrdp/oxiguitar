# Changelog

All notable changes to OxiGuitar. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- The plugin manager says plainly when a restart is needed: a plugin can't be unloaded while OxiGuitar runs, so a plugin unticked while in use is marked as staying in use until OxiGuitar restarts, the window shows "Restart OxiGuitar to apply these changes" while any change waits, and the footer says it too.
- The plugin manager (M2 slice 3), part of the program: **Tools → Plugins…** opens a window of its own listing every plugin file in the plugin folders, with its name, version, folder and file, and what became of it (loaded, not loaded yet, disabled, not used because another file holds the same plugin, or why it can't be used). A tickbox enables or disables each plugin from the next start, written to `disabled` in settings.json. It only lists and switches: it never downloads, copies, installs or removes a file. `oxiguitar --safe-mode` starts with no plugin used at all, while the manager still lists them, and Help → About lists the plugin folders in the order they are searched.
- Plugins' tabs in the window (M2 slice 3): each plugin tab joins the panel its manifest names, after OxiGuitar's own, and shows the plugin's widgets drawn with the window's own buttons, tickboxes, sliders, fields, drop-downs and lists, and its canvases drawn by our renderer at the screen's pixel density, as large as the room allows, following Dark Interface. A thread of their own asks the plugins and draws the canvases, so the window never waits for a plugin, and drags a plugin hasn't answered yet are merged. The app tells plugins when a score is opened or changed (a tool), and hands the open score to plugins that ask, shared rather than copied.
- Plugin tabs and pushed events (M2 slice 3; plugin interface 1.1, added at the end of every enum, so 1.0 plugins keep working). A plugin declares tabs in its manifest (an id, a title, one of the window's four areas) and fills them with standard widgets (labels, buttons, toggles, sliders, fields, drop-downs, lists) that the core draws in its own style, plus canvases it draws itself with a display list (lines, rectangles, paths, text placed with the core's fonts, colours by role) and receives pointer events on in its own units. Contents the core can't show are refused with a sentence saying why. A plugin subscribes to events (score opened, changed or closed; selection; playback position); the host pushes them in order on a thread of its own that sleeps until there is something to deliver, so nothing polls, and a slow plugin gets the latest position rather than a backlog. Plugins can ask for the open score and for their tab to be redrawn. The SDK gains `Tab` and `Plugin::tab`/`event`, `Host::score`/`redraw`, and `check` verifies every tab's contents; the contract suite checks tabs, widgets, canvases and events through a plugin's file, and the test plugin has two tabs and every event. `oxiguitar-display`'s `wire` feature turns a canvas into the core's display list, and the fuzz target `plugin_tab` draws any answer a plugin could give.
- The Guitar Pro format plugins (M2): `gp3.oxp`, `gp4.oxp`, `gp5.oxp`, `gpx.oxp` and `gp.oxp`, one per format, each a thin crate over `oxiguitar-formats` carrying only its own reader (from 475 KB for Guitar Pro 3 to 796 KB for Guitar Pro 7–8, which alone holds the ZIP code). Each recognises its files from the signatures in its manifest, without being loaded. They read every Guitar Pro file exactly as the readers did inside the program: all 159 files of the fixtures, the references and the private corpus, score and import log, byte for byte.
- `scripts/build-plugins.sh` builds our plugins, each on its own, and puts them where a build from source looks for them (`target/lib/oxiguitar/plugins/` on Linux, `target/PlugIns/` on macOS, `plugins\` beside the program on Windows). Until the core and the basic plugins are packaged apart, every package (.deb, .rpm, AppImage, Windows zip, .dmg) installs the five plugins in the program's own plugin folder, and the test builds of develop carry them too.
- A file no installed plugin recognises is refused with a sentence that says what to do: a bug report when a plugin declares its extension but doesn't recognise it, a feature request otherwise, both at the issue tracker; with no plugin at all, where to get them. A plugin that would open it but is disabled or can't be used says so.
- Tests through the plugins' files (`oxiguitar-plugin-test`'s `ours`): the contract for all five, each reading only its own format, every file read exactly as in-process, the refusals. A fuzz target for the plugins' side of the interface (`plugin_dispatch`), and clippy on each reader alone in CI.
- Plugins load (M2, ADR 0008). The SDK for plugin authors, `oxiguitar-plugin` (MIT OR Apache-2.0): a plugin implements `Plugin` and the traits for what it contributes (`FormatReader`, `FormatWriter`, `Service`), writes `manifest.json`, and calls `export_plugin!`, which puts the manifest in the `oxg_manifest` section and exports the entry symbol; plugin authors write no `unsafe`. A panic in a plugin is caught and reported as an error, and the plugin goes on working. `cargo test` checks the manifest against the plugin (unknown keys, declared formats and services that aren't implemented, the version).
- The plugin host in `oxiguitar-host`: at start it reads every plugin's manifest with the `object` crate, which reads only the manifest's section (30 manifests in about 1 ms), and loads nothing. From the manifests it knows the formats that can be opened and saved and recognises a file by its signatures, offers instruments by the instrument classes they play, and finds services. A plugin is loaded the first time one of its contributions is used, and never unloaded. Services are chosen by their conditions (system, processor, display system), their priority and whether their probe says they work here, unless settings.json pins one (`services`); `disabled` in settings.json keeps plugins from loading; of several files holding the same plugin, the highest version wins (then the earlier folder). Plugins send footer messages, keep their own settings under their id in settings.json, and call services through the host. The footer names the plugins found and every plugin file that can't be used, and why (damaged, another system's, a newer interface).
- The plugin contract suite, `oxiguitar-plugin-test` (a library, a program for plugin authors, and the tests): builds a plugin as an `.oxp` file and checks it through the host (manifest read without loading, it starts, missing contributions are "not found", damaged input and an empty score never crash it, every service answers its probe). A test plugin (`plugins/test`, never shipped) runs every part of the interface end to end on every system CI tests, including errors, panics and a plugin calling a service through the host. A test checks that `unsafe` code is allowed only in the host's loader and the SDK's export glue, and CI's speed budget now includes reading 30 plugin manifests (under 10 ms).
- The plugin interface, `oxiguitar-plugin-api` (M2, ADR 0008), under MIT OR Apache-2.0 so plugins may use any GPL-compatible licence (Mateus, 18 Oct 2026): the two C tables a plugin and the host exchange, the messages that cross them (encoded with postcard, each enum's variant positions pinned by a test), the manifest (JSON in the `oxg_manifest` section, read without loading code; unknown keys ignored so newer plugins load in older hosts), format signatures that recognise a file from its bytes or its ZIP members, instrument classes for every General MIDI program, and the score as plugins see it (version 1, a mirror of the model with its encoding pinned). `oxiguitar-model`'s `wire` feature converts between the two: every fixture, visual reference and corpus file crosses without loss.

- ADR 0007: macOS "open document" events (a double-click in Finder, Open With, a drop on the Dock icon) wait for winit or Slint to report them, the same way Wayland drops do (ADR 0006); CONTRIBUTING.md lists it under "Known platform gaps". CONTRIBUTING.md gains "Design principles": no polling ever, no hacks, speed, elegance.
- The .deb's Maintainer field points to the GitHub issue tracker by decision, never to a personal address.
- The window takes its final shape (M2): a toolbar of sections under the menus (File: Open, Save, Export PDF; Edit: Undo, Redo: only what is clicked often), four tabbed areas around the page (top: Player; bottom: Tracks, Mixer; left: Palette; right: Inspector) that collapse to their tab strip, resize, and hide from View → Panels (F7 left, F8 bottom), and a footer line with the latest message that expands into every message of the session. The player's controls (rewind, play, play selection, pause, stop, count-in, loop, metronome) and its output choice are in the top area, greyed out until an output plugin is installed. Tabs that wait for the editor or the player show what they will hold. Our own icons, in `assets/icons/ui/`.
- On launch the app makes sure its folders exist: on Linux, following the freedesktop XDG convention, `settings.json` (created as `{}`) in `~/.config/oxiguitar/` and the `plugins` folder in `~/.local/share/oxiguitar/`; on macOS both in `~/Library/Application Support/OxiGuitar/`, on Windows in `%APPDATA%\OxiGuitar\` (`OXIGUITAR_HOME` puts everything in one folder). It looks for plugin files (`.oxp`) in the user's and the system's plugin folders (or those `plugin_folders` lists in settings.json), and says in the footer when no output plugin, or no plugin that reads and writes files, is installed, with where to get them. New crate `oxiguitar-host`.
- The View menu remembers its settings in settings.json (`view`: dark interface, dark page, dynamics, layout, paper). A new View → Dark Interface tick switches the window's own colours; the interface is dark by default and the page white.
- Manual: "The window" and "Settings and plugins".

### Changed

- Over the page, the mouse wheel now scrolls and Shift + wheel zooms the score around the pointer (Mateus, 18 Oct 2026; it was the other way round). Ctrl + wheel still zooms the interface.

- The plan, amended again (Mateus, 18 Oct 2026; ADR 0008, "Amendments"): the plugin manager is part of the core, not a plugin, and opens only from Tools → Plugins as a separate window. It lists every plugin file in the plugin folders with its version, folder and state, and enables or disables it from the next start; it doesn't install, remove, download or copy anything, and draws no settings forms. The app makes no distinction between our plugins and others' anywhere; the privacy promises, which cover only what we publish, are stated in the README and the manual. M2's slice 3 builds plugin tabs and events pushed to plugins, then the manager.
- The app and `oxiguitar-cli` open files only through format plugins; the core no longer reads any format itself and no longer depends on `oxiguitar-formats`. With no plugin installed, nothing opens. `oxiguitar-cli` uses the app's plugin folders and settings.json, read only (it creates and saves nothing), and `info` and `detect` name the plugin that read the file (the format's name comes from the plugin, so it no longer shows the minor version, such as 5.10). File → Open's filter lists the extensions the installed plugins read. Guitar Pro 1–2 files, which no plugin reads, are refused like any other file nothing recognises.
- `oxiguitar-formats` has one Cargo feature per reader (`gp3`, `gp4`, `gp5`, `gpx`, `gp`, all on by default) and a `plugin` feature with what the format plugins share. The Guitar Pro 3–5 reader leaves out other versions' code when their feature is off, and refuses a header whose version number doesn't match its own ("5.10", not "50.1"). Formats without a reader are now plainly "not supported" (the `NeedsPlugin` error is gone).
- `oxiguitar-cli manifest` became an example of `oxiguitar-formats` (`cargo run -p oxiguitar-formats --example corpus_manifest -- FOLDER…`), since it describes files by the readers' own detection; its output is unchanged.
- The speed budget reads its score through the Guitar Pro 7–8 plugin and holds the first run, which loads the plugin, to the budget as well; the visual references are read through it too. CI's tests run with default features (with `--all-features`, two plugin crates in one test program would both export the entry symbol), and NET-5 runs with our plugins installed.
- The plan, amended (Mateus, 18 Oct 2026; ADR 0008, "Amendments"): PDF export stays in the core as a feature of the viewer, and Infer Key Signatures as a feature of the editor, so M2's slice 2 (making them plugins) is dropped; other tools and other exports are still plugins. The AppImage will come with a zip of the basic plugins beside it, like the Windows zip and the .dmg. The core will recognise no file format itself: what it opens is what the installed plugins recognise, and a file none recognises is refused with a request for a feature, or for a bug report when an installed plugin declares its extension.
- The app and plugins share one copy of settings.json, so neither overwrites the other's keys. A settings.json that couldn't be read at start is no longer overwritten when the View menu changes: it stays as it is until it is fixed.
- cargo-deny accepts RUSTSEC-2026-0370, 0371 and 0372 (zvariant, zvariant_derive and zbus_names are unmaintained since zbus 6 took them in, published 17 Oct 2026). They come in through zbus 5, which Slint 1.18's winit backend and AccessKit still use; revisit on the next Slint upgrade.
- The plan: the plugin system moves forward to M2, before the editor (Mateus, 18 Oct 2026). The core keeps reading, editing, writing, showing and the player's controls; every file format (one plugin each), sound, export, tool and platform-specific feature becomes a plugin. Design in `docs/design/plugins.md`, decision record ADR 0008 (accepted with Mateus's answers: native plugins, XDG folders on Linux, two Linux builds (Wayland, deprecated X11), packages `oxiguitar` and `oxiguitar-plugins-basic`, Debian main as the goal, instrument classes for output plugins, v1.0 = viewer, editor, player and plugins); ROADMAP.md and ARCHITECTURE.md renumbered and redrawn (M2 plugins and window shell, M3 editor, M4 player = v1.0, M5 Guitar Pro 8 parity, M6 format plugins, M7 NAM, M8 RSE, M9 drums and hardware, M10 mobile).
- The mouse wheel over the page zooms the score, keeping the point under the pointer in place; Shift + wheel scrolls. Ctrl + wheel still zooms the whole interface, anywhere in the window.
- The background around the page is always dark (`#242528`), with or without Dark Page.
- Messages (errors, tool reports, exports) go to the footer instead of the status pill over the score, and stay until a newer one arrives.
- The app no longer builds Slint's system-tray support (ksni), which it never used; `deny.toml` no longer needs the Unlicense.

### Fixed

- The speed-budget tests shared one temporary folder, and whichever finished first deleted it under the other: an occasional failure unrelated to speed. Each test now has its own folder.
- Release builds: the draft-release job unpacked the Windows .zip packages into folders and failed on them (v0.1.0's first tag build). It now keeps every package as it was uploaded, checks that there are nine package files and that each zip holds oxiguitar.exe, and makes the checksums on every build, so a build by hand tests it too; only a tag creates the draft release.

## [0.1.0] - 2026-10-17

Milestone M1 (the viewer) is complete. This is OxiGuitar's first tagged release: open a Guitar Pro 3–8 file and view it in standard notation, tablature, or both.

### Added

- Neighbouring dynamics keep apart: like chord names, each marking stays under its beat and the music opens up so it ends before the next one (ppp and pp on quarter notes touched).
- Release packages (`.github/workflows/release.yml`, scripts in `scripts/package/`): a portable .exe in a zip for Windows, an AppImage, a .deb and an .rpm for Linux, each for x86_64 and ARM64, and a universal .dmg for macOS, none code-signed. A v* tag builds them into a draft release with SHA256SUMS; started by hand, they stay under the run for 14 days. Each package is installed and started in CI: the .deb on Debian sid, the .rpm on Fedora, the AppImage on Ubuntu. The .deb, .rpm and .dmg register the Guitar Pro file types OxiGuitar opens (.gp, .gpx, .gp5, .gp4, .gp3; UI-4) with the placeholder icon as the file icon; the .exe carries the icon and its name and version for Explorer and Task Manager. Every package includes THIRD-PARTY-LICENSES.html, generated from `Cargo.lock` with cargo-about.
- Directions are engraved on their own line above the top staff: segno and coda signs (and their doubles) at the start of their bar; Fine, D.C., D.S. and their "al Coda", "al Double Coda" and "al Fine" forms, and "To Coda" with its sign, ending at the end of their bar.
- The user manual, published on GitHub Pages (https://mateusrdp.github.io/oxiguitar/, source in `docs/manual/`, built with mdBook by the "Manual" workflow): installing, opening files, the four layouts, tracks and notation buttons, score and interface zoom, dark page and dynamics, Infer Key Signatures, PDF export, keyboard and mouse. On macOS, interface zoom now uses ⌘ like the menus' shortcuts.
- Release packages (`.github/workflows/release.yml`, scripts in `scripts/package/`): a portable .exe in a zip for Windows, an AppImage, a .deb and an .rpm for Linux, each for x86_64 and ARM64, and a universal .dmg for macOS, none code-signed. A v* tag builds them into a draft release with SHA256SUMS; started by hand, they stay under the run for 14 days, each downloadable as the package file itself rather than a zip. Each package is installed and started in CI: the .deb on Debian sid, the .rpm on Fedora, the AppImage on Ubuntu. The .deb, .rpm and .dmg register the Guitar Pro file types OxiGuitar opens (.gp, .gpx, .gp5, .gp4, .gp3; UI-4) with the placeholder icon as the file icon; the .exe carries the icon and its name and version for Explorer and Task Manager. Every package includes THIRD-PARTY-LICENSES.html, generated from `Cargo.lock` with cargo-about.
- `scripts/install-desktop-entry.sh` also registers the Guitar Pro file types, and takes an AppImage as the program.
- The speed budget (M1): a 300-bar, 8-track file opens in under a second, from reading the file to the first tiles. A test opens a generated score as dense and as long as a real Guitar Pro 7 file the way the window does (0.18 s, or 0.23 s with all eight tracks shown), and CI's "Speed budget" job holds release builds to it. See `docs/testing.md`.
- `oxiguitar-testgen`: test scores written in a short text notation and saved as Guitar Pro 7 files, starting with the speed budget's eight-track band song. Test code only.
- Fuzzing of every file reader (M1): cargo-fuzz targets for Guitar Pro 3–5, Guitar Pro 6, Guitar Pro 7 and 8, the GPIF XML, and any file through format detection (`fuzz/`), seeded from the public fixtures. The "Fuzz" workflow runs each for four minutes on pull requests that touch a reader, and for six hours per reader when started by hand. M1's target is six hours per reader without a crash (lowered from 24); the first run met it on 16 October 2026, with no crash, hang or out-of-memory input in any reader.
- Visual regression tests (M1): fifty generated reference scores, kept in `fixtures/reference/` as Guitar Pro 7 files with the pictures they engrave to, read back through the reader, engraved and compared with a tolerance on every CI target. Failures leave the drawn picture and a picture of the differences, uploaded by CI. `OXIGUITAR_BLESS=1` writes new pictures after an intended change. See `docs/testing.md`.
- `oxiguitar-formats` reads Guitar Pro 6 (.gpx) and Guitar Pro 7 and 8 (.gp) files: the BCFZ/BCFS and ZIP containers and the GPIF score inside, with an import log of anything not carried over yet. Which notation each track shows (standard, tablature) comes from the file. All 15 GPX and GP files in the test corpus open; alphaTab reads the same notes from every one of them, bar for bar.
- Guitar Pro 6 tied notes with a stale fret take the fret of the note they continue; flat "bends" that Guitar Pro 7 writes on tied notes are dropped.
- Public test songs in Guitar Pro 6 and 7 format (`fixtures/gp/oxiguitar-test-song.gpx` and `.gp`), checked against the Guitar Pro 5 reader on the same music.
- Corpus tests (`cargo test --release -p oxiguitar-formats --test corpus`) that read every GPX and GP file and compare six songs saved in two formats; they run only where `corpus/files/` holds the private corpus.
- `docs/formats/guitar-pro-6-8.md`: what we learned about the containers and GPIF.
- Section markers keep their rehearsal letter (Guitar Pro 7 and 8); `oxiguitar-cli info` shows it as `[A] "Intro"`.
- `oxiguitar-layout`, the engraver: turns a score into one display list per page in the Page layout (VIEW-3). Standard notation and tablature share columns bar by bar (VIEW-1), and several tracks line up in one score (VIEW-4). It draws clefs, key and time signatures with key changes and cancelling naturals, notes, chords, rests, accidentals that follow the key within a bar, ledger lines, stems and beams by voice, flags, dots, ties, tuplets, repeats, volta brackets, double and final bar lines, sections, tempo, chord names, beat text, bar numbers, and the score header with credits and tuning (VIEW-6). Tablature-only tracks show their rhythm around the tab (VIEW-2), and drum tracks use a drum staff with the General MIDI kit. Spacing follows duration and widens where symbols would touch; systems are stretched to the line, an overfull bar is squeezed, and a system taller than the page is engraved with a smaller staff (NOT-1, NOT-2, NOT-4).
- `oxiguitar-cli render <file> --png PREFIX --pdf FILE`: engraves a score into PNG pages and a PDF, light or dark (`--dark`), with a choice of tracks (`--tracks 1,3` or `all`).
- Engraving tests: public fixtures, damaged scores, a 300-bar 8-track score (engraved in well under half a second), and every Guitar Pro file of the private corpus with all its tracks, checking that everything lands on the page and every glyph exists in the fonts (`cargo test --release -p oxiguitar-layout --test engrave`).
- `docs/design/engraving.md`: how the engraver works, and what it does not draw yet.
- CI shows failing tests as an annotation on the pull request.
- Effects and marks in the engraving (TAB-1, NOT-3):
  - **Between notes:** hammer-ons and pull-offs (arcs with H/P), slides between notes and into or out of them, bends and releases with their amounts.
  - **Along the music:** vibrato, trills, palm mute, let ring, harmonic kinds, tap/slap/pop, w/bar, fade in, pick strokes.
  - **On notes:** natural harmonics (diamond heads, `<12>` on tab), ghost notes in parentheses, accents and staccato, tremolo strokes, strums.
  - **Grace notes** before their main note.
  - **Dynamics** where the marking changes.
  - **Lyrics** under the staff, with room made for each syllable.

  Marks that run along the music get lanes of their own above the tablature, so they never collide.
- Chord diagrams of the chords used, in the score header (VIEW-6).
- `oxiguitar-tools` and the Tools menu's first tool, **Infer Key Signatures**: for scores that leave every bar in C major, as most tabs do, it sets key signatures from the notes, with key changes where the music modulates, and leaves chromatic music in C. It runs only when the user asks; the engraver shows what the file says. Every tool has the same small shape, so plugins can add tools in M5. `oxiguitar-cli tools` lists the tools and `render --tool ID` applies one.

- Characters the text font lacks, such as ♯ and ♭ in chord names, come from the music font.
- Tuplets that do not take the usual time are marked with their ratio, such as 5:3; the usual ones keep their single number.
- Tempo marks are shown only where the tempo changes, and never on top of each other.
- In the score header, the tuning goes under the credits when the two would meet.
- Track names at the start of each system when several tracks are shown: full names on the first system, short names after, as in Guitar Pro's multitrack view.
- The other three staff layouts (VIEW-3), checked against the Guitar Pro 8 user guide: **Vertical** (lines fill the window's width, one long sheet), **Horizontal** (every bar on one line) and **Parchment** (page-width lines with no page breaks, Guitar Pro 8's Page – Scroll). `oxiguitar-cli render --layout NAME [--width PT]`; long sheets are cut into PNGs of at most 8192 pixels.
- Letter paper beside A4 (`--paper letter`). PDFs are always in pages, whatever the layout.
- **The desktop app**, `oxiguitar` (crate `oxiguitar-app`, Slint), the first version of the viewer. File → Open (or `oxiguitar FILE`) opens any Guitar Pro 3–8 file; the score is drawn in tiles on a worker thread, so the window never waits. View → Layout (Page, Vertical, Horizontal, Parchment), Dark Page and Dynamics; the track list (F8) shows any set of tracks; the score-zoom slider (25–400 %) and interface zoom (Ctrl + wheel, Ctrl + + / − / 0); the Tools menu with Infer Key Signatures, greyed out with its reason when it cannot run; File → Export PDF… of the shown tracks on A4 or Letter (EXP-1); errors and tool reports in a status line. ### Changed

- The track list has no show tick any more: a track's notation buttons show and hide it (both off hides it, either button shows it again), which saves room and leaves one control per job.
- No View → Multitrack menu item either: showing a track's own buttons already shows it alongside the others, so the menu item did nothing the buttons didn't, for one more control to keep in sync.
- With Dark Page, the canvas behind the page is a touch darker, so it reads as its own grey rather than matching the menus and track list, while staying lighter than those.
- Guitar Pro 6–8 files open about twice as fast: the XML tree keeps every element in one list and borrows names and text from the file instead of copying them (`oxiguitar-cli info` on Seek and Destroy: 0.11 s instead of 0.26 s). The scores and import logs read from every GPX and GP file in the corpus are unchanged.
- Guitar Pro 6–8 beats keep their dynamic as a marking (`BeatEffects::dynamic`) as well as giving it to their notes as velocity, so the engraver can tell a marking from a velocity.
- Beat text at the end of a system no longer runs off the page; the page test now checks where each text ends, not only where it starts.
- Plan (Mateus, 16 Oct 2026): the core reads and writes Guitar Pro formats only. MuseScore, MusicXML, ABC and MIDI files, and tab derivation for staves without tablature, become plugins after the plugin system (M5). M1's "98 % of the corpus opens" counts Guitar Pro files only. Visual regression uses 50 generated reference scores kept in the repository. ROADMAP and README follow. Opening one of those files now says that a format plugin will open it, instead of "not supported yet".
- Voice 1's stems point up even when it is the only voice in the bar (Mateus, 16 Oct 2026). Stems on the staff now always follow the voice number.
- Stems follow the voice number, as Mateus asked after the first review: voices 1 and 3 up, voices 2 and 4 down, whenever a voice other than the first has notes in the bar (before, the first voice with notes went up and all others down, so voice 3 pointed down and a lone voice 2 pointed up). Drums always follow it; voice 1 alone still points its stems by where its notes sit. Rests of several voices move up or down by the same rule.
- Rhythm on tablature (tab-only tracks) shows every voice with the same rule: voices 1 and 3 with stems up above the tab, voices 2 and 4 with stems down below it. Before, only voice 1 was drawn, with stems down. Rests on tab move out of the staff into each voice's rhythm area, so they no longer cover fret numbers.
- Chord names stay over their beat. Instead of pushing a name sideways when it would touch the next one, the music opens up to make room. On tab-only tracks the chord names sit above the upward stems.
- Drum notes from Guitar Pro 3–5 files are kept as pitches (the General MIDI drum) rather than as string and fret, as the score model intends for instruments without strings.
